# 项目当前问题与改进方向

## 一、当前主要问题

### 1. 业务主线不够聚焦

项目已经包含内容发布、问答、评论、关注、搜索、通知、推荐、身份认证和管理端审核等功能，但功能之间的重点还不够突出。整体更像一个功能较完整的社区基础版本，校友社区的差异化价值还没有被充分体现。

如果直接写进简历，容易变成 MySQL、Redis、RabbitMQ、Elasticsearch、AI 等技术名词的罗列，面试官不容易快速理解项目解决了什么实际问题。

### 2. 异步链路的可靠性和一致性不足

内容审核、通知、热度更新和搜索索引同步使用了 RabbitMQ、Redis 和 Elasticsearch，但部分逻辑是在数据库事务提交后直接发送消息或更新其他系统。发送失败时目前主要记录日志，缺少统一的事件状态、重试、补偿和人工处理机制。

因此可能出现数据库已经保存成功，但审核任务没有投递、ES 没有同步或通知没有发送的情况。当前代码具备消息队列的基础设施，但还不能完整证明消息一定能够最终处理成功。

### 3. 测试和验证证据不够完整

后端自动化测试目前较少，已有 API 测试文档存在时间较早、统计结果不完全一致等问题，不能完全作为当前代码质量的证明。小程序 TypeScript 检查也还有类型错误，说明三端代码还没有完全收口。

目前缺少对权限控制、重复点赞、审核失败、MQ 重试、ES 同步失败等关键异常场景的系统测试，也缺少基于明确数据量和并发条件的性能测试结果。

### 4. 配置和权限存在开发环境痕迹

项目中还保留了测试登录逻辑，管理端登录流程也偏向本地演示用途。正式包装项目时，需要明确普通用户、管理员和审核人员的权限边界，并补充管理员操作日志，避免只能说明“有 JWT”，却无法讲清楚完整的权限控制方案。

本地配置中还存在敏感信息管理问题，需要确认密钥没有提交到代码仓库，并通过环境变量或示例配置进行隔离。

### 5. 代码和文档还需要进一步收口

部分核心业务逻辑集中在较大的 Service 类中，后续维护和测试成本较高。接口文档、部署文档、测试报告和当前实际运行配置也存在不同步的情况，例如依赖服务地址变更后，旧文档仍可能保留原来的配置。

项目目前可以在本地运行，但还缺少一份从环境检查、依赖启动、后端启动到三端验证的统一运行说明，这会影响面试时的远程演示和项目复现。

### 6. AI/RAG 功能缺少实际评估

AI 搜索和混合检索可以作为项目亮点，但目前更适合作为辅助功能。现阶段缺少检索准确率、响应耗时、模型调用失败处理和调用成本等数据，也没有明确证明混合检索比普通 Elasticsearch 搜索好多少。

如果没有评测数据，不建议把 RAG 描述成项目的核心能力或生产级方案，否则面试时容易被追问向量存储、召回率、评测集和成本控制。

## 二、优先改进方向

1. **先完成现有功能的收口**：修复小程序类型错误，重新编译并验证登录、发布、详情、互动和管理审核流程。
2. **补齐关键测试**：重点覆盖管理员权限、内容审核、重复点赞、消息重试、ES 同步失败和封禁用户等场景，并重新生成一份统一的 API 测试报告。
3. **完善异步一致性**：引入 Outbox 事件表、消息幂等消费、失败重试和人工补偿，让内容审核、通知和搜索同步形成可靠链路。
4. **加强社区治理**：补充管理员操作日志、内容驳回后重新提交、限流、禁言或回收站等功能，体现社区产品的实际运营需求。
5. **突出校友社区特色**：可以围绕学校、学院、专业、地区、毕业年份或话题订阅设计圈层 Feed，避免项目看起来只是普通论坛。
6. **统一项目文档和环境**：整理启动说明、依赖服务检查、测试账号和配置示例，确保项目能够稳定复现和演示。
7. **最后再包装 AI 功能**：为 AI 搜索增加来源展示和简单评测数据，把它作为加分项，而不是继续堆叠更多 AI 技术。
