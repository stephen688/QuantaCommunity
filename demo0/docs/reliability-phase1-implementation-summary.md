# 第一阶段并发、幂等与可靠事件改造总结

> 核对依据：`reliability-phase1-plan.md`、`outbox-plan.md`、当前后端和管理端代码。
>
> 当前结论：两份计划中的代码改造已经闭环，关键路径已有自动化测试和页面验收。生产发布前仍需在正式环境执行数据库迁移、确认依赖健康并观察真实流量指标。

## 一、Phase 1 完成情况

| 改造项 | 状态 | 实现结果 |

| 唯一约束与历史数据 | 已完成 | 已核对点赞、收藏、关注关系表的联合唯一约束，当前数据库未发现重复关系。 |

## 二、Outbox / Inbox 完成情况

- 业务变更与 Outbox 在同一 MySQL 事务提交，回滚不会遗留事件。
- Dispatcher 使用租约抢占、实例所有权校验、Confirm ACK 和 Return 判断；断连、NACK、Return 和超时进入重试，耗尽后进入 `DEAD`。
- 审核、通知、Feed、热度和 ES 校准消息都要求 `eventId`，旧的无 `eventId` 兼容处理入口已移除。
- 消费者通过 Inbox 防重复、租约接管和所有权校验；业务结果与 `SUCCESS` 在同一事务完成的链路保持原有服务分层。
- 重试和死信生产统一等待 RabbitMQ Confirm/Return，发布失败时不会错误 ACK 原消息。
- Feed、热度和 ES 消费采用“事件只触发校准、最终重新读取当前状态”的实现，避免乱序消息恢复旧状态。
- 每天清理超过 30 天的 `SENT` / `SUCCESS`；存在未完成或 `DEAD` Inbox 的 Outbox 不删除。
- 定时记录死亡事件数和最长积压时间；管理端概览接口提供状态数量、平均发送延迟、最长积压和重试分布。

## 三、管理端

新增 `/events` 事件中心，沿用现有 Element Plus、页面标题、筛选区、表格、抽屉和橙色主题：

- Outbox / Inbox 双页签、条件查询、分页和详情；
- 只有 `DEAD` 状态显示重放操作，重放前二次确认；
- 双管理员并发重放通过条件更新保证只有一个成功；
- 左侧菜单显示事件中心，存在死亡事件时显示数量红点；
- 桌面和 768px 窄屏已做真实浏览器检查。

- 消费者单元测试：重复审核、重复通知、DEAD/DLQ、Feed/热度/ES 校准通过；
- `npm run build`：管理端生产构建通过；

## 五、上线前环境门槛

代码完成不等于生产环境已经切换。上线前仍需：

1. 在目标数据库执行并核对 Outbox / Inbox 迁移与联合唯一索引；
2. 使用目标 RabbitMQ 检查所有主队列、重试队列、死信队列及绑定；
3. 确认运行实例加载的是本次构建产物；
4. 观察 `DEAD`、最长积压、平均发送延迟和重试分布，再决定是否调整阈值。
