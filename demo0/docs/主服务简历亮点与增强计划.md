## 二、增量候选：三个加法按 ROI 排序

### 🥇 A. Caffeine + Redis 多级缓存 —— 首推，且不是可选项

> ⚠️ **关键发现**：简历"个人优势"第 3 条已写"具备多级缓存（Caffeine + Redis）实战经验"，
> 但整个 demo0 **没有任何 Caffeine 依赖和 `@Cacheable`** —— 这是当前简历最大的诚信风险。
> **必须补实现，否则改简历。**

**落地场景（全部现成）：**

| 场景 | 缓存问题覆盖 |
|---|---|
| 热榜聚合（`search:trending:all` 现在是裸 Redis） | 加 Caffeine 一级 + Redis 二级 |
| 帖子详情 / 用户信息（读多写少） | 写操作 `afterCommit` 驱逐（复用现有事务后同步模式） |
| 详情接口天然存在"查不存在" | **穿透**：空值缓存 |
| 热点 key 失效瞬间重建 | **击穿**：单飞互斥（singleflight）或逻辑过期 |
| 大量 key 同时到期 | **雪崩**：TTL 随机抖动 |

**工作量**：1-2 天。面试缓存三件套必考，性价比最高。

### 🥈 B. 私信 + Quanta 群聊 —— 次推

- WebSocket / STOMP / 定向推送已就绪，只差会话模型：`conversation` + `message` 两张表
- **群聊用读扩散**：成员按 `lastReadId` 算未读，不写扩散 —— "中小规模社区读写扩散选型"本身就是一道面试题
- 私信 2-3 天，群聊再加 2-3 天
- 可复用现成 Outbox → MQ → WebSocket 链路做离线消息

### 🥉 C. 用户画像推荐 —— 可做，但要克制

**素材全有**：浏览历史、点赞/收藏 ZSET、professional / life 双池。

**为什么克制（不是"太大不好做"，轻量版两三天就能写完）：**

1. **数据撑不起更复杂的算法**：协同过滤（CF）需要足够多用户行为交集才有意义。校园社区几百活跃用户、行为矩阵极度稀疏，item-based CF 算出的"相似帖子"大概率是噪声 —— **这个数据规模下，加权重排就是正解**，不是偷懒。
   - 面试官问"为什么不用协同过滤"：答"行为稀疏 + 冷启动 + 不可解释，选择内容侧画像加权" → 加分
   - 如果写了 CF 被问"怎么处理数据稀疏"答不上来 → 减分
2. **用词决定追问深度**：写"推荐算法/推荐系统"，会按推荐系统工程师标准被问（召回怎么做的？离线指标？AUC？A/B？）—— 这些都没有。写"基于用户画像的个性化重排"，追问范围收敛在真实做的东西里。
   - ⚠️ **简历上别写"推荐算法"三个字，写"用户画像重排"**

**面试话术（诚实地讲成工业链路的简化版，反而最好）：**

> "我的推荐链路是工业界'召回 → 精排 → 重排'的简化：**召回**用 Redis 双池 ZSET（全量/热度），
> **精排**是热度分（时间衰减公式），**重排**用用户画像分（行为加权 + 融合系数）对召回结果重排序。"

显示理解推荐系统的架构分层，比半成品 CF 值钱得多。

**落地定义（2-3 天）：**

- **画像生成**：浏览×1 / 点赞×2 / 收藏×3，带时间衰减，聚合成用户的"专业↔生活"兴趣分（双池维度天然现成）
- **重排公式**：`finalScore = α·热度分 + (1-α)·画像匹配分`；α 随用户成熟度动态调整（新用户偏热度、老用户偏画像）—— "新老人用户差异化"又能讲一分钟
- **画像存储**：Redis Hash 存每用户兴趣权重，行为事件后异步更新（复用现成 MQ 链路）

### 附加：并发场景 —— 别造秒杀，已有三个真实故事

1. **点赞幂等**（防计数漂移）
2. **Inbox 抢占**（防多实例重复消费）
3. **Lua 限流**（原子窗口）

这三个比硬造"秒杀系统"真实得多，任何深度的追问都打不穿。
另外：项目里装了 JMeter 但上次运行没产出数据 —— **对点赞接口和 Feed 拉取跑一轮真实压测**，拿到 QPS / P99 写进简历，说服力翻倍。

## 五、包结构重构决策：按域分包，不改 DDD

### 诊断：乱的不是 MVC，是三个具体问题

1. **上帝服务（最严重）**：`ContentServiceImpl` 1983 行 / 46 个方法，同时管发布、审核对接、推荐流、热度计算、点赞、收藏、举报、浏览历史、搜索、曝光去重、Redis 维护；`CommentServiceImpl` 也近 1000 行。"乱"的真正来源在这里——换包名解决不了 1983 行。
2. **两种分包逻辑混放**：顶层 `controller/ service/ mapper/ entity/`（按层分柜）与 `es/ mq/ rag/ security/`（按技术分柜）平铺混放，业务边界在包名上不可见。缺一个 `infra/` 归拢层。
3. **小疙瘩**：`modertion/` 拼写错（→ moderation）；`BaseContext`（ThreadLocal 上下文）错放 `entity/`；`handler/` 只有 1 个类；`policy/` 只有 1 个类。

### 为什么不改 DDD

| 角度 | 结论 |
|---|---|
| 成本 | 299 个文件全搬家 + 概念重造（聚合根/值对象/领域服务/仓储），现有仅 11 个测试兜不住，纯风险 1-2 周 |
| 面试风险 | 半吊子 DDD 一问"聚合根是什么、限界上下文怎么划"就露馅，比诚实的 MVC 更减分 |
| 收益 | 校园社区规模下，DDD 战术模式解决不了实际问题（问题是类太大，不是建模不够） |
| 适用时机 | 未来真拆微服务、多团队协作时再说 |

**简历口径**：写"按业务域分包的模块化单体 + 事件驱动（Outbox/Inbox）"，不写 DDD。

### 该做的重构：package-by-feature（模块化单体）

层保留在域内部，按业务域分柜：

```
com.quanta.demo0
├── content/          # 帖子：发布/详情/管理
│   ├── controller/ service/ mapper/ dto/ vo/
├── interaction/      # 点赞/收藏/举报/浏览历史
├── comment/          # 评论与回答
├── feed/             # 推荐流 + 热度榜（曝光去重、预热）
├── search/           # ES 检索与对账
├── notify/           # 通知
├── follow/           # 关注社交
├── moderation/       # 审核（修 modertion 拼写，policy/ 并入）
├── identity/         # 身份认证考试
├── security/         # JWT/权限/限流（横切安全）
├── rag/              # RAG（保持现装）
└── infra/            # 归拢技术包：mq/(outbox,consumer,producer)、es、oss、config、common(context,utils,result,exception)
```

配套核心动作：**拆 ContentServiceImpl** → ContentCommandService（发布/删除）、InteractionService（赞/藏/举报）、FeedRecommendService（推荐/曝光/热度）、ContentQueryService（各类列表），拆完每类 300-500 行。以后 Caffeine、画像重排都有明确落点。

**收益**：1-2 天工作量；面试多一个真实故事（"模块化单体、按域分包、域间走 service 接口，为将来拆微服务留了缝"）。

### 时机：放在主线最后，别现在动

重构动几乎所有 import；Caffeine、画像重排是加新类。**先加完再一起搬家，只搬一次。**
