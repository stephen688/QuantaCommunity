# 社区项目功能优化方案

## 一、优化目标

将项目从“功能较完整的普通社区”进一步包装成“面向高校校友的互助与经验沉淀社区”。

本轮只围绕三个方向优化：

1. 校友互助闭环；
2. 发布前相似内容检测；
3. 可解释的个性化推荐。

这三个方向都可以复用现有的内容、回答、身份认证、搜索、推荐、通知和消息队列能力，不需要为了增加亮点而额外拆分微服务或堆叠新技术。

## 二、方向一：校友互助闭环

### 1. 功能定位

将普通内容发布升级为“提出问题—校友回答—采纳答案—问题解决—经验沉淀”的完整流程。

适合的校友场景包括：

- 求职和内推；
- 租房和城市选择；
- 升学、留学和回国；
- 行业经验咨询；
- 课程、校园生活和校友活动。

### 2. 建议增加的功能

- 内容增加“求助/经验分享”等场景类型；
- 增加问题状态：待解决、处理中、已解决；
- 支持提问者采纳回答；
- 展示“已认证校友”标识；
- 支持学校、学院、专业、毕业年份、城市等筛选条件；
- 问题解决后沉淀为可搜索的经验内容；
- 采纳答案后给回答者发送通知，并增加“感谢/有帮助”反馈。

### 3. 实现重点

- 对问题状态和回答采纳设计明确的状态流转，避免重复采纳或重复通知；
- 只有提问者或管理员可以改变问题状态；
- 认证信息只展示必要字段，敏感信息需要支持隐藏；
- 采纳、感谢、通知等操作需要考虑重复提交和消息重试；
- 搜索结果中突出“已解决”和“已采纳”内容。

### 4. 面试价值

可以把项目从普通论坛描述为校友互助产品，并重点讲解状态机、权限控制、幂等处理、通知链路和内容沉淀，而不是只介绍发帖和评论接口。

## 四、方向三：可解释的个性化推荐

### 1. 功能定位

在现有最新、热门和曝光过滤的基础上，引入用户的明确兴趣和负反馈，让用户知道内容为什么被推荐，并且能够主动调整推荐结果。

### 2. 建议增加的功能

- 关注学校、专业、城市和话题；
- 对内容进行“不感兴趣”或“减少此类内容”操作；
- 支持屏蔽某个话题或内容类型；
- 在卡片上展示“因为你关注了某话题”等推荐原因；
- 推荐流混合最新、关注、热门和兴趣内容；
- 新用户根据身份标签和热门内容完成冷启动。

### 3. 实现顺序

第一阶段使用规则评分，不需要引入复杂机器学习模型。可以综合考虑关注关系、内容类型、用户兴趣、点赞收藏、发布时间、内容质量和曝光次数。

第二阶段再根据用户行为调整权重，并增加内容多样性控制，避免首页长期展示同一类内容。

推荐结果仍然可以使用 Redis ZSet 管理候选内容，但需要额外记录用户的兴趣、负反馈和曝光行为。

### 4. 需要注意的问题

- 新用户没有行为数据时，要有最新和热门内容兜底；
- 用户点“不感兴趣”后，内容不能立即重新出现；
- 同一用户短时间内不能重复看到相同内容；
- 推荐失败时要能降级到最新内容；
- 不要在没有真实数据的情况下声称推荐效果提升了多少。

### 5. 面试价值

可以围绕冷启动、候选集、负反馈、曝光去重、推荐解释和 Redis 数据结构展开，体现对社区 Feed 流的理解，比简单描述“使用 Redis 做推荐”更有深度。

## 五、建议实施顺序

### 第一阶段：先做互助闭环

优先增加问题状态、回答采纳、认证标识和校友场景标签，先让产品主线成立。

### 第二阶段：增加相似内容检测

先使用 Elasticsearch 完成可用版本，再将向量检索作为增强能力，并补充来源展示和降级处理。

### 第三阶段：升级推荐流

增加兴趣选择、不感兴趣、推荐原因和行为记录，在现有 Redis Feed 流上逐步迭代。

## 六、简历表达方向

完成后可以围绕下面这句话包装项目：

> 面向高校校友的互助内容社区，围绕问题解决状态、答案采纳和身份标签形成校友互助闭环；基于 Elasticsearch 和向量检索实现发布前相似内容召回，减少重复内容；在 Redis Feed 流基础上加入用户兴趣、负反馈和推荐解释，提升内容分发的可控性。

建议优先做完第一、第二阶段，再决定是否继续深入推荐算法。这样项目会有清晰的产品主线，也能保留后端面试需要的搜索、推荐、缓存和异步链路亮点。

## 七、安全与并发方面的补充优化

### 1. 统一安全体系

项目目前已有 JWT、Redis 登录态和管理员校验，但权限逻辑主要依赖自定义拦截器，部分 `@RequireAuth` 规则还需要进一步收口。建议引入 Spring Security，保留现有微信登录和 Redis Token 机制，统一处理 JWT 解析、普通用户/认证校友/管理员角色以及方法级权限控制。

建议将当前用户信息放入 Spring Security 的 `SecurityContext`，使用请求级规则保护管理端，再通过 `@PreAuthorize` 保护需要认证校友或管理员权限的业务方法。同时补充登录限流、上传校验、生产环境 CORS 限制、WebSocket 鉴权和管理员操作日志。

重点不是单纯增加依赖，而是让认证、授权、401/403 返回、管理员操作审计和 WebSocket 鉴权形成统一链路。面试时可以重点说明为什么保留 Redis Token 校验，以及管理员权限发生变化后如何让旧 Token 失效。

### 2. 补齐业务并发和幂等

点赞、收藏、关注等操作目前存在“先查询、再插入或更新”的并发窗口，回答采纳也可能出现同时操作导致状态覆盖的问题。建议增加用户与目标对象的联合唯一约束，使用原子更新和明确的目标状态接口，避免重复提交导致重复记录或计数错误。

点赞、收藏和关注可以采用“数据库唯一约束 + 插入成功后更新计数”的方式保证幂等，接口也可以从简单的 toggle 改为明确传入目标状态。回答采纳可以使用行锁或乐观锁控制同一个问题的并发修改，避免两个回答同时被采纳。

Redis 主要用于缓存和加速，不作为最终数据事实来源；Redis 更新失败时应通过事件重试或定期校准恢复。面试时可以通过重复请求、并发请求和 Redis 暂不可用三组测试证明改造效果。

### 3. 完善异步消息一致性

内容审核、通知、热度和搜索同步依赖 RabbitMQ，但数据库提交成功后，后续消息或 Redis/Elasticsearch 更新仍可能失败。建议增加 Outbox 事件表、事件 ID 幂等消费、失败重试和死信补偿，确保业务数据与异步任务最终能够恢复一致。

Outbox 事件应与业务数据在同一个数据库事务中写入，再由后台任务可靠投递 MQ。消费者处理成功后再 ACK，并使用 `eventId` 防止重复落库；超过重试次数的消息进入死信队列，由管理端提供查看和重新执行能力。

这部分可以作为后端面试中的工程亮点，重点展示消息重复、服务重启、MQ 暂停和 ES 暂不可用等故障场景下的处理结果，而不是简单罗列使用了 RabbitMQ、Redis 或分布式锁。
