
# 项目细节优化与可靠性改造复盘（面试版）

> 本文不是简单罗列“我用了哪些技术”，而是记录我在项目中发现了什么问题、为什么原来的实现不可靠、我是怎样逐步缩小问题范围并做技术取舍的，以及最终如何证明改造有效。
>
> 本次改造主要分成两层：
>
> 1. 先解决 MySQL 内部的业务并发与幂等问题；
> 2. 再解决 MySQL、RabbitMQ、Redis、Elasticsearch 之间的异步可靠性问题。

## 一、我对问题的总体判断

这个项目原来的正常流程基本可以工作，但“请求成功一次”不代表系统在重复请求、并发请求、服务宕机和网络抖动时仍然正确。

我把问题分成了三个层次：

1. **业务状态本身是否正确**：例如同一个用户只能点赞一次，同一个问题只能有一个采纳答案；
2. **跨系统事件是否会丢**：例如帖子已经保存到 MySQL，但审核 MQ 没有发送成功；
3. **失败后是否能发现和恢复**：例如消息重试多次后失败，管理员能否查到原因并安全重放。

我的改造顺序也是按照这三个层次展开。因为如果点赞计数本身就可能并发出错，即使后面加了 Outbox，也只是在“可靠地传播一个错误结果”。所以我先完成业务幂等，再做异步链路可靠性。

## 二、优化一：点赞、收藏和关注的并发幂等

### 1. 原来的问题在哪里

原来的部分接口采用“切换状态”的思路：

1. 先查询用户当前是否点赞；
2. 如果没有点赞就新增，如果已经点赞就取消；
3. 再修改内容表中的点赞计数。

这在单次请求中没有问题，但有两个隐患。

第一个隐患是**请求语义不幂等**。例如客户端发出一次点赞请求，因为网络超时没有收到响应，于是自动重试。第一次请求已经把状态改成“已点赞”，第二次相同请求又按照切换逻辑把它改回“未点赞”。用户明明想点赞，最终结果却可能相反。

第二个隐患是典型的 **check-then-act 并发竞争**。两个请求可能同时查询到“尚未点赞”，随后都尝试插入明细并增加计数。即使数据库唯一索引挡住了第二条明细，业务代码如果没有正确判断实际影响行数，主表计数仍可能增加两次。

我在检查 Mapper 时还发现一个更隐蔽的问题：部分插入使用了：

```sql
ON DUPLICATE KEY UPDATE id = id
```

它看起来像是“重复时什么也不做”，但项目当前 JDBC/MySQL 环境的实际实验中，重复分支仍可能返回 `1`。如果业务层把“影响行数等于 1”理解成“刚刚新增成功”，就会继续增加点赞数并产生 Outbox 事件。这是一个 SQL 表面幂等、业务判断却不幂等的问题。

涉及的位置主要包括：

- 内容点赞、内容收藏：`ContentMapper.xml`；
- 回答点赞：`QuestionMapper.xml`；
- 评论点赞：`CommentMapper.xml`；
- 用户关注：`FollowMapper.xml`；
- 对应业务入口：`ContentServiceImpl`、`AnswerServiceImpl`、`CommentServiceImpl`、`FollowServiceImpl`。

### 2. 我的优化思路

我没有一上来引入 Redisson 或分布式锁，而是先问了两个问题：

1. 这类约束能不能由数据库直接表达？
2. 能不能把接口改造成目标状态，而不是状态切换？

答案都是可以。

首先，把请求语义改成“设置为已点赞 / 设置为未点赞”，而不是“切换一下”。这样相同请求执行一次或多次，目标状态都相同。

其次，用联合唯一索引作为最后一道防线：

- 内容点赞：`content_id + user_id`；
- 内容收藏：`content_id + user_id`；
- 回答点赞：`answer_id + user_id`；
- 评论点赞：`comment_id + user_id`；
- 用户关注：`user_id + follow_user_id`。

最后，将关系插入统一改为 `INSERT IGNORE`，并且只有插入真正影响一行时才增加计数、写入 Outbox。取消操作也只有删除真正影响一行时才减少计数。

核心逻辑可以概括为：

```text
目标是已点赞：
    INSERT IGNORE 点赞明细
    如果 affectedRows == 1：点赞数 +1
    如果 affectedRows == 0：说明原本已经点赞，直接成功

目标是未点赞：
    DELETE 点赞明细
    如果 affectedRows == 1：点赞数 -1
    如果 affectedRows == 0：说明原本已经取消，直接成功
```

主表计数更新仍使用 `GREATEST(0, count + delta)` 作为额外保护，但我没有把它当成主要幂等方案。真正决定是否修改计数的依据，是明细表是否发生了实际变化。

### 3. 为什么这样设计

我的思考是：**能用数据库唯一约束解决的确定性约束，不应该优先交给分布式锁。**

分布式锁会增加 Redis 可用性、锁超时、锁续期和异常释放等新问题，而唯一索引天然覆盖所有应用实例，约束也更接近数据本身。应用层负责表达目标状态，数据库负责最终裁决，这个边界更简单。

### 4. 优化后的好处

- 客户端超时重试不会把点赞状态反向切换；
- 多个实例同时收到请求，也只能产生一条关系记录；
- 明细没有变化时，计数和后续事件也不会变化；
- Redis 状态过期不会影响 MySQL 最终结果；
- 方案不依赖分布式锁，部署和维护成本更低。

### 5. 我如何验证

我使用 MySQL 8.0.43 Testcontainers 做了真实并发测试，而不只是 Mock Mapper：

- 同一点赞重复执行，明细只有一条，计数只增加一次；
- 两个线程同时收藏，只有一个插入成功；
- 两个线程同时关注，只有一个有效关系；
- 重复取消点赞和收藏，计数不会变成负数；
- 最终明细数量与主表计数一致。

## 三、优化二：回答采纳的并发冲突

### 1. 原来的问题在哪里

采纳回答不是单行数据更新，而是一个组合操作：

1. 清除这个问题原来的采纳答案；
2. 将新的回答设置为已采纳；
3. 发送通知并同步搜索状态。

如果两个管理员或两个请求同时采纳不同答案，两边都可能先完成“清除旧答案”，再分别设置自己的答案。在缺少串行化边界时，中间状态和最终结果都不稳定，甚至可能出现多个已采纳答案。

### 2. 我的优化方式

我把“问题记录”作为并发控制的聚合根。在采纳事务中，先对问题执行 `SELECT ... FOR UPDATE`，拿到同一个问题的行锁，再执行：

1. 判断目标回答是否已经被采纳；
2. 清除旧采纳状态；
3. 设置新采纳状态；
4. 只有状态真正变化时才登记通知和搜索校准事件。

两个不同答案同时被采纳时，后来的请求必须等待前一个事务完成，因此同一个问题的采纳操作被串行化。

### 3. 为什么锁问题而不是锁回答

真正的约束是“一个问题只能有一个采纳答案”，约束范围是问题，而不是某一条回答。如果分别锁两个回答，两个请求锁的是不同记录，仍然不能互相阻止。锁定问题记录才与业务约束的粒度一致。

### 4. 优化后的好处

- 同一个问题最终只能有一个采纳答案；
- 重复采纳同一个答案可以直接幂等返回；
- 通知只在状态真正变化时产生，避免重复提醒；
- 没有引入全局锁，不同问题之间仍然可以并发操作。

## 四、优化三：MySQL 与 Redis 的一致性边界

### 1. 原来的问题在哪里

MySQL 和 Redis 不能加入同一个本地事务。如果业务事务还没有提交就先更新 Redis，后面 MySQL 回滚，缓存中就会留下一个数据库里不存在的状态。

反过来，如果为了保证数据库正确而先提交 MySQL，提交后 Redis 更新又可能失败。因此这里不能承诺强一致，需要明确谁是最终数据源以及失败后如何恢复。

### 2. 我的处理方式

我将 MySQL 定义为最终事实来源，Redis 只承担查询加速：

- 数据库事务成功提交后，再通过事务同步回调更新 Redis；
- 数据库事务回滚时，不执行缓存修改；
- Redis 更新失败时不反向回滚已经提交的业务数据；
- 日志中记录明确的 `businessType`、`userId`、`targetId` 和 `targetState`；
- 后续读取可以从 MySQL 重新加载缓存。

### 3. 这里的取舍

我没有为了追求表面上的“全部成功”而把 Redis 异常抛回客户端。因为此时 MySQL 已经提交，如果接口返回失败，客户端重试反而可能扩大重复操作。我的选择是保证核心数据正确，缓存允许短暂不一致并可重建。

### 4. 优化后的好处

- 不会出现数据库回滚但缓存提前成功的脏状态；
- Redis 短时不可用不会破坏核心业务事务；
- 日志具备可检索的业务上下文，排查时不只看到一条模糊异常；
- 明确了“数据库是事实，缓存是派生数据”的架构边界。

## 五、优化四：为什么要引入 Outbox

### 1. 原来的问题在哪里

原来的异步流程大多是：

```text
提交 MySQL 事务
    ↓
afterCommit 中直接发送 RabbitMQ / 更新 ES
```

这里存在一个无法用普通本地事务覆盖的时间窗口：

- MySQL 已经提交，但应用在发送 MQ 前宕机，业务数据存在，事件永久丢失；
- MQ 已经收到消息，但应用没有收到确认，发送方可能再次发送；
- 外部系统更新失败时，只有日志，没有持久化的重试入口；
- 失败事件无法统一查询，也无法让管理员安全恢复。

例如帖子发布成功后，审核消息如果丢失，帖子会一直停留在待审核状态。单纯增加 `try-catch` 或立即重试，并不能解决进程已经退出、机器重启或长时间依赖不可用的问题。

### 2. 我的核心判断

我没有尝试实现跨 MySQL 和 RabbitMQ 的分布式事务，而是选择本地消息表 Outbox：

```text
同一个 MySQL 事务：
    写业务数据
    写 Outbox 事件

事务提交后：
    后台 Dispatcher 持续扫描并投递 RabbitMQ
```

这样只需要依赖 MySQL 本地事务，就能保证“业务数据和待发送事件要么一起成功，要么一起回滚”。RabbitMQ 暂时不可用时，业务事件仍然保存在数据库中，恢复后可以继续发送。

### 3. 为什么选择至少一次，而不是承诺恰好一次

如果 RabbitMQ 已经收到消息，但应用在把 Outbox 标记为 `SENT` 前宕机，恢复后必然会再次发送同一个事件。仅靠发送端无法区分消息究竟有没有被消费者处理。

因此我没有做不现实的“恰好一次”承诺，而是明确采用：

```text
至少一次投递 + 消费端幂等 = 业务结果只生效一次
```

这也是后面设计 Inbox 的原因。

### 4. Outbox 事件保存什么

Outbox 保存：

- 全局唯一 `eventId`；
- `eventType`；
- 业务对象类型和 ID；
- 最小化 JSON payload；
- 投递状态、重试次数、下次重试时间；
- 租约、错误和人工重放审计信息。

我没有直接序列化完整业务实体，因为实体字段会持续变化，也可能带入不需要甚至敏感的信息。帖子审核事件只保留审核真正需要的标题、正文、发布者和图片 URL，并对 UTF-8 序列化结果增加 32 KB 上限。超过上限时让业务事务整体回滚，避免保存一条永远发不出去的事件。

### 5. 优化后的好处

- MySQL 成功但 MQ 丢失的问题变成了可持久化、可重试的问题；
- RabbitMQ 长时间不可用也不会让事件只存在于内存中；
- 每条事件都有状态、次数和最后错误，可查询、可审计；
- 业务代码只负责登记事件，外部投递逻辑得到统一收口。

## 六、优化五：多实例 Outbox Dispatcher 的租约设计

### 1. 原来的潜在问题

如果后台部署多个实例，所有实例都会定时扫描 Outbox。如果只是普通 `SELECT` 后再更新，多个实例可能同时读取并发送同一条事件。

即使使用锁，也不能在等待 RabbitMQ Confirm 的几秒内一直持有数据库事务，否则会造成长事务、连接占用和锁竞争。

### 2. 我的设计

Dispatcher 分成两个阶段。

第一阶段是短事务抢占：

1. 使用 `FOR UPDATE SKIP LOCKED` 选择到期的 `PENDING`，以及租约过期的 `PROCESSING`；
2. 将事件改为 `PROCESSING`；
3. 写入 `locked_by` 和 `locked_until`；
4. 立即提交事务。

第二阶段在事务外发送 RabbitMQ，最后根据结果更新事件状态。

默认每秒扫描一次，每批最多 50 条，租约 60 秒。这样多个实例可以并行扫描不同记录，而不会因为一条正在发送的事件长期占住数据库锁。

### 3. 为什么同时需要 `locked_until` 和 `locked_by`

`locked_until` 解决的是“谁可以接管”：实例宕机后，租约过期，其他实例可以继续处理。

`locked_by` 解决的是“谁有权写最终结果”。例如实例 A 发生长时间网络卡顿，租约过期后实例 B 接管并处理成功。此时 A 又恢复，如果最终更新只检查状态、不检查所有者，A 可能把 B 的结果覆盖掉。

因此标记 `SENT`、重试或 `DEAD` 时，SQL 必须同时满足：

```sql
status = 'PROCESSING'
AND locked_by = 当前实例
```

这相当于一个轻量的所有权令牌。

### 4. 优化后的好处

- 支持多个后端实例水平扩展；
- 一个实例宕机不会让事件永久卡在处理中；
- 旧实例恢复后不能覆盖新实例结果；
- RabbitMQ 网络等待不占用数据库长事务。

## 七、优化六：RabbitMQ Confirm 和 Return 的可靠判断

### 1. 原来的问题在哪里

调用 `RabbitTemplate.convertAndSend` 没有抛异常，只能说明发送调用完成，不能直接说明消息已经进入目标队列。

RabbitMQ 有两个容易混淆的结果：

- **Confirm ACK**：交换机已经接收消息；
- **Return**：交换机接收了消息，但没有任何队列匹配路由键。

因此只判断 Confirm ACK 是不够的。ACK 和 Return 可以同时出现，此时消息仍然没有进入业务队列。

### 2. 我的处理方式

我开启 `mandatory=true`，并使用 `CorrelationData(eventId)` 关联每次发布结果。只有同时满足以下条件才把 Outbox 标记为 `SENT`：

```text
Confirm = ACK
没有 ReturnedMessage
没有超时
当前实例仍然拥有租约
```

Confirm NACK、Return、等待超时和发送异常都进入统一失败处理。

普通 Outbox 最多失败 6 次，等待时间依次增长；消费者的重试和死信发布也统一通过可靠发布器等待 Confirm/Return，避免“重试消息其实没发出去，却把原消息 ACK 掉”。

### 3. 优化后的好处

- 能发现交换机存在但路由键或队列绑定错误的情况；
- 不会把未路由消息误标记为发送成功；
- 重试消息和死信消息也具备相同的发布确认语义；
- 网络超时、NACK 和拓扑配置错误可以通过 `last_error` 区分排查。

## 八、优化七：使用 Inbox 保证消费者幂等

### 1. 原来的问题在哪里

Outbox 采用至少一次投递后，消息重复是正常现象：

- 发送成功但 Outbox 未及时标记 `SENT`；
- 消费者业务已经提交但 ACK 前宕机；
- RabbitMQ 因连接中断重新投递未 ACK 消息。

如果消费者每次都直接执行业务，重复审核可能反复修改状态，重复通知可能插入多条通知记录，热度也可能被重复累加。

### 2. 我的设计

每个消费者在处理前，使用 `consumer_name + event_id` 登记 Inbox，并建立联合唯一索引。

Inbox 的状态包括：

- `PROCESSING`：正在处理；
- `RETRYING`：等待重试；
- `SUCCESS`：已经成功；
- `DEAD`：重试耗尽。

处理规则是：

1. 第一次收到事件，插入 Inbox 并取得处理租约；
2. 已经是 `SUCCESS`，直接 ACK，不再重复执行业务；
3. 正在被其他实例处理且租约未过期，进入延迟重试；
4. 租约已经过期，可以由其他实例条件抢占；
5. 业务成功后将 Inbox 改为 `SUCCESS`，事务提交后再 ACK；
6. 更新结果时同样校验 `locked_by`。

对于通知消费，我把“通知落库”和“Inbox 标记 SUCCESS”放进同一个 MySQL 事务。这样不会出现通知已经保存但 Inbox 仍然失败，导致下次重复插入通知的情况。

### 3. 为什么 Inbox 不复制 payload

Inbox 主要负责记录“某个消费者是否已经处理某个事件”，不是另一份消息存储。重复保存 payload 会增加存储和清理复杂度，也可能产生两份内容不一致。

所以 Inbox 只保存事件身份、业务对象、状态、租约和错误信息，详情及重放时通过 `eventId` 读取原 Outbox payload。

### 4. 优化后的好处

- 相同审核事件重复到达，只产生一次有效状态变更；
- 相同通知事件重复到达，数据库只有一条通知；
- 消费实例宕机后可以由其他实例恢复；
- Inbox 状态提供了消费侧独立的重试、错误和审计视角。

## 九、优化八：失败重试、DEAD 与 DLQ

### 1. 原来的问题在哪里

无限立即重试会占满线程和队列，也会持续冲击已经不可用的依赖；但直接丢弃又会造成业务事件永久丢失。

另一个问题是，如果消费者先 ACK 原消息，再尝试发送重试消息，一旦重试发布失败，原消息和重试消息都会丢失。

### 2. 我的处理方式

- 失败时先记录 Inbox 错误、重试次数和下次处理时间；
- 通过可靠发布器将消息发送到延迟重试队列；
- 确认重试消息真正发布成功后，才 ACK 原消息；
- 超过最大消费重试次数后，将 Inbox 标记为 `DEAD`，消息进入 DLQ；
- 如果发布重试或死信消息失败，原消息执行 NACK 并重新入队，不能静默丢失。

Outbox 发布失败和消费者业务失败分别维护状态。因为 Outbox 只能证明消息是否可靠到达 MQ，不能代替消费者对业务结果做幂等和失败处理。

### 3. 优化后的好处

- 短暂故障可以自动恢复；
- 持续故障不会无限热循环；
- 重试或死信发布失败时，原消息仍然保留；
- `DEAD` 和 DLQ 为人工处理提供明确入口。

---

## 十、优化九：Feed、热度和 ES 的乱序最终一致性

### 1. 原来的问题在哪里

异步消息不能假设严格按业务发生顺序到达。例如一个帖子先发布后删除，但“删除事件”可能先到，“发布事件”后到。如果消费者盲目执行事件中的动作，旧的发布事件可能把已经删除的帖子重新加入 Feed 或 ES。

热度更新如果直接消费“点赞数 +1”这种增量消息，重复或乱序也会造成累计错误。

### 2. 我的优化思路

我把这些消息从“命令”改成“校准提醒”：事件只告诉消费者哪个业务对象需要重新检查，最终状态必须重新读取 MySQL。

- Feed：重新读取内容当前状态，决定是加入还是删除；
- 热度：读取当前点赞、收藏、评论数据，重新计算完整分数并覆盖 Redis；
- Elasticsearch：读取当前内容，满足存在、审核通过且未删除时 upsert，否则 delete。

这样即使旧事件最后才到，它读取到的仍然是 MySQL 最新状态，不会恢复历史状态。

### 3. 优化后的好处

- 对重复消息和乱序消息天然更稳健；
- Redis ZSET 和 ES 文档使用确定 ID 覆盖，操作可重复执行；
- 最终结果始终向 MySQL 当前状态收敛；
- 消费者不需要维护复杂的事件先后版本比较。

### 4. 这里的边界

这是一种最终一致性方案，不代表 Redis 或 ES 在每一毫秒都与 MySQL 完全相同。如果业务以后要求严格的版本顺序，还可以增加业务版本号或更新时间比较。但当前社区项目更看重可恢复性和实现复杂度之间的平衡，所以我选择了“重新读取事实源并覆盖”的方案。

## 十一、优化十：管理端事件中心与人工重放

### 1. 原来的问题在哪里

只有自动重试还不够。事件最终进入 `DEAD` 后，如果只能登录服务器查日志，排查和恢复成本很高，也缺少操作审计。

### 2. 我的优化方式

我在原有管理端增加 `/events` 事件中心，并保持项目原有 Element Plus、页面标题、筛选区、表格、抽屉和橙色视觉风格，没有另起一套设计体系。

页面提供：

- Outbox / Inbox 双页签；
- 按事件 ID、消费者、事件类型、状态、业务对象和时间范围查询；
- 事件详情和原 payload 查看；
- `PENDING / PROCESSING / SENT / DEAD` 等状态概览；
- 平均发送延迟、最长积压时间和重试分布；
- DEAD 数量菜单红点；
- DEAD 事件人工重放和二次确认。

### 3. 重放为什么只允许 DEAD

普通 `SENT` 事件不允许直接重放。因为相同 `eventId` 可能被已经成功的 Inbox 拦截；如果换一个新 `eventId`，又可能重复产生业务结果。

因此 Outbox 和 Inbox 都只允许 `DEAD` 通过带状态条件的 SQL 重放：

```sql
UPDATE ...
SET status = 'PENDING', ...
WHERE event_id = ?
  AND status = 'DEAD'
```

两个管理员同时点击时，只有一个请求能影响一行。系统同时记录管理员 ID、重放时间和重放次数。

### 4. 数据清理策略

- 每天清理 30 天前已完成的 `SENT` Outbox 和 `SUCCESS` Inbox；
- `PROCESSING`、`RETRYING`、`DEAD` 长期保留；
- 只要还有未完成 Inbox，原 Outbox 就不能删除，因为人工重放仍然依赖原 payload。

### 5. 优化后的好处

- 失败事件从“只能查日志”变成可查询的业务对象；
- 管理员可以在权限体系内完成安全恢复；
- 并发重放有数据库条件保护，不依赖前端按钮防重复；
- 错误、次数和操作人形成完整审计链路。

## 十三、这次改造体现的核心思考

### 1. 先保证事实源正确，再保证事件可靠

Outbox 不能修复点赞自身的并发错误。所以我先让 MySQL 内部状态具备幂等和并发正确性，再把正确结果可靠地传播出去。

### 2. 不追求不现实的“恰好一次”

分布式系统中，发送成功和本地记录成功之间总有故障窗口。与其承诺做不到的恰好一次，不如明确采用至少一次投递，并在消费端通过 Inbox 和覆盖式写入实现业务幂等。

### 3. 把数据库约束放在最接近数据的位置

目标状态、唯一索引、影响行数和行锁共同构成正确性基础。应用层判断只负责优化体验，数据库约束才是多实例下的最终防线。

### 4. 区分核心数据和派生数据

MySQL 中的业务记录、通知记录是核心事实；Redis、ES、Feed 和 WebSocket 是派生或展示能力。派生数据失败可以重建，不能反向破坏已经正确提交的核心事务。

### 5. 自动恢复和人工恢复都要设计

重试解决短暂故障，租约解决实例宕机，DEAD/DLQ 解决持续故障，事件中心解决人工排查和恢复。只实现其中一层，可靠性链路都不完整。

### 6. 可观测性不是最后补日志

事件状态、`last_error`、重试次数、积压时间、重放人和重放时间都是数据模型的一部分，而不是发生事故后临时补的日志。

## 十四、面试时可以这样讲

### 1. 一分钟版本

> 我在项目里做过一次从业务幂等到异步可靠性的完整改造。最初点赞、收藏和关注存在重复请求与并发计数风险，部分 SQL 用 `ON DUPLICATE KEY UPDATE id=id`，在当前 JDBC 环境下重复分支仍可能被当成有效更新。我先把接口改成目标状态语义，用联合唯一索引、`INSERT IGNORE` 和实际影响行数保证明细与计数一致；回答采纳则锁定问题行，保证一个问题只有一个采纳答案。
>
> 在此基础上，我把原来事务提交后直接发 MQ 的链路改成 Outbox。业务数据和事件在同一个 MySQL 事务提交，Dispatcher 用 `SKIP LOCKED` 和租约支持多实例抢占，RabbitMQ 同时判断 Confirm 和 Return。因为投递语义是至少一次，我又用 Inbox 的 `consumerName + eventId` 唯一约束保证消费幂等，并对 Feed、热度和 ES 使用重新读取 MySQL 后覆盖的校准方式解决乱序。最后增加管理端事件中心、DEAD 重放和 26 个自动化测试，包括真实 MySQL、RabbitMQ 断连恢复。这个改造让我比较系统地处理了正确性、可恢复性和可观测性三个层面。

### 2. 如果面试官问“最难的点是什么”

可以回答：

> 最难的不是把消息存进 Outbox，而是把所有故障窗口想完整。例如 Confirm ACK 不等于消息已经路由到队列；旧实例租约过期后恢复，不能覆盖接管实例；通知落库与 Inbox SUCCESS 必须同事务；重试消息发布失败时不能 ACK 原消息。这些边界如果漏掉，系统表面上有 Outbox，实际仍然可能丢消息或重复执行。

### 3. 如果面试官问“为什么不用分布式锁”

可以回答：

> 点赞和关注的约束可以用联合唯一索引直接表达，回答采纳也只需要锁问题这一条聚合根记录。数据库约束覆盖所有实例，失败语义更明确。引入分布式锁会增加锁续期、超时和 Redis 可用性问题，所以当前规模下没有必要。Outbox 多实例抢占则使用 MySQL 8 的 `SKIP LOCKED` 和租约，已经满足需求。

### 4. 如果面试官问“为什么不是恰好一次”

可以回答：

> MQ 已经收到消息但发送方还没把数据库改成 SENT 时发生宕机，恢复后一定可能重复发送。跨 MySQL 和 RabbitMQ 无法靠普通本地事务消除这个窗口。因此我选择至少一次投递，并通过 Inbox 唯一键、条件更新和幂等业务操作保证结果只生效一次，这是更诚实也更可实现的方案。

### 5. 如果面试官问“这个方案还有什么不足”

可以回答：

> 当前方案使用数据库轮询，优点是简单、依赖少，但事件量非常大时会增加数据库扫描压力。后续可以根据监控数据调整批次和索引，或者演进到 CDC。当前 Redis 和 ES 是最终一致，不适合要求毫秒级强一致的业务。另外上线前还需要在正式环境核对迁移、RabbitMQ 拓扑和告警阈值。我会把代码完成和生产验证分开表述，不会因为本地测试通过就直接声称线上完全可靠。

## 十五、最终收益总结

| 维度 | 优化前 | 优化后 |
| --- | --- | --- |
| 重复请求 | 可能发生状态反转或重复计数 | 目标状态语义，重复执行结果不变 |
| 并发请求 | 依赖先查后写，存在竞争窗口 | 唯一索引、影响行数和行锁共同约束 |
| 数据与 MQ | 提交后直接发送，宕机可能丢事件 | 业务数据和 Outbox 同事务，失败可重试 |
| 多实例发送 | 可能重复扫描和覆盖状态 | `SKIP LOCKED`、租约和所有权校验 |
| RabbitMQ 判断 | 发送调用成功容易被误认为投递成功 | Confirm、Return、超时同时判断 |
| 重复消费 | 可能重复审核、重复通知 | Inbox 防重，成功后直接 ACK |
| 外部系统乱序 | 旧事件可能恢复旧状态 | 重新读取 MySQL，覆盖式校准 |
| 故障处理 | 依赖日志和人工排查 | 自动重试、DEAD、DLQ、管理端重放 |
| 可观测性 | 缺少统一事件视角 | 状态、错误、延迟、积压、重试和审计完整记录 |

这次优化的价值不只是“增加了 Outbox 表”，而是把一个只能在正常路径运行的异步系统，改造成了能够面对重复、并发、断连、宕机和人工恢复的可靠链路，同时保留了清晰的技术边界和后续演进空间。
