# 第一阶段计划：业务并发与幂等改造

## 一、阶段目标

先解决点赞、收藏、关注和回答采纳在重复请求或并发请求下可能出现的重复记录、计数错误和状态覆盖问题。

## 二、具体改造计划

### 1. 先检查并整理现有数据

检查点赞、收藏、关注等表中是否已经存在重复数据，同时确认数据库中现有的索引和约束。

如果已有重复记录，需要先清理，再增加联合唯一约束，例如“同一个用户只能点赞同一条内容一次”。这样数据库可以作为最后一道防线，即使两个请求同时到达，也不会插入两条相同记录。

涉及的主要关系包括：

- 内容点赞：内容 ID + 用户 ID；
- 内容收藏：内容 ID + 用户 ID；
- 回答点赞：回答 ID + 用户 ID；
- 评论点赞：评论 ID + 用户 ID；
- 用户关注：用户 ID + 被关注用户 ID。

### 2. 将点赞、收藏和关注改为幂等操作

现在部分接口使用“切换状态”的方式：系统先查询当前状态，再决定点赞还是取消。重复点击或两个请求同时执行时，最终结果可能不稳定。

建议改为明确告诉后端目标状态，例如“设置为已点赞”或“设置为未点赞”。如果用户已经处于目标状态，接口直接返回成功，不再重复修改数据。

数据库插入或删除真正成功后，才更新对应计数，避免点赞明细没有变化但计数仍然加减。Redis 只负责加速查询，最终状态以 MySQL 为准。

### 3. 解决回答采纳的并发冲突

采纳回答时，需要保证同一个问题在同一时刻只有一个请求能够修改采纳状态。

建议在事务中锁定对应的问题记录，再取消旧采纳并设置新采纳。如果重复采纳同一个回答，直接返回成功；如果两个回答同时被采纳，后执行的请求需要等待或返回状态冲突，不能产生两个已采纳答案。

只有采纳状态真正发生变化时才发送通知，避免重复通知回答者。

### 4. 统一事务后的 Redis 处理

点赞、收藏和关注的数据库事务成功后，再更新 Redis。数据库事务失败时不能提前修改缓存。

如果 Redis 更新失败，本阶段先记录明确的业务类型、用户 ID 和目标 ID，并允许后续从数据库重新加载缓存。完整的自动重试和补偿将在下一阶段通过 Outbox 和事件机制处理。

### 5. 补充并发与幂等测试

至少验证以下场景：

- 同一个点赞请求重复执行，数据库只有一条记录，计数只增加一次；
- 多个请求同时收藏同一内容，最终只有一条收藏记录；
- 多个请求同时关注同一用户，最终只有一个有效关注关系；
- 两个回答同时执行采纳，最终只能有一个采纳答案；
- 取消点赞或收藏重复执行时，计数不会变成负数；
- 操作结束后，明细表数量与内容表中的计数保持一致。

## 三、本阶段不做的内容

- 不引入 Redisson 或分布式锁；
- 不进行完整的 Spring Security 迁移；
- 不实现 Outbox 和 MQ 失败补偿；
- 不调整推荐算法和 RAG 功能；
- 不进行无关的前后端页面改造。

## 四、阶段完成标准

数据库具备必要的唯一约束，点赞、收藏、关注和采纳接口在重复请求与并发请求下结果稳定，并有自动化测试证明不会出现重复记录、错误计数或多个采纳答案。

完成这一阶段后，再进入第二阶段：将审核、通知、热度和搜索同步改造成 Outbox + MQ 幂等消费的可靠异步链路。
