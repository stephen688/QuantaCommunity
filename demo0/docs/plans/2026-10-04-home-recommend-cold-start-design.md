# 首页推荐冷启动与曝光设计

日期：2026-10-04。状态：用户已确认产品选项，待实施；本文不代表功能已完成。

## 1. 用户确认的八项决定

| 决策 | 本次采用 |
|---|---|
| 入口 | “推荐／热度”，默认推荐 |
| 游客 | 本地随机游客标识，只用于曝光去重，不建立游客兴趣画像 |
| 探索比例 | 所有用户约20%，每5条最多1条；不足由主推荐补齐 |
| 探索范围 | 最近7天的可见、同分类、未曝光帖子；尽量覆盖不同作者和标签 |
| 曝光 | 进入可视区域才回传，每条曝光独立24小时失效 |
| 耗尽 | 扩大召回找未看内容，确实耗尽提示暂无新内容，用户主动选择再看已看内容 |
| 本轮范围 | 只改推荐流；热度排行榜另做 |
| 后续热榜 | 计划每5分钟统一重算并发布版本；本轮不实现 |

## 2. 现有代码事实

- `miniprogram/pages/home/index.ts` 的 `latest` 标签是“默认”，`hot` 是“热度”；真实请求配置 `USE_MOCK=false`。
- `FeedQueryServiceImpl.recommend` 将未指定场景、`latest`、`recommend` 都分流到画像重排，`hot` 使用 Redis 分数游标。`latest` 当前并非纯时间排序。
- `RecommendRerankServiceImpl` 热门、最新各取150条，合并后统一算分；已有行为画像与独立显式偏好加分。游客没有画像、显式偏好，按现算热度排序。
- 画像流仅登录用户有曝光 SET，返回页面即写曝光，集合续期24小时；游客跳过曝光，也忽略分页游标，重复请求可能返回相同头部。
- 热度流不读写曝光。本轮保持这一路的排序、分页和刷新语义。
- 首页 `startFeedTimer` 每45秒调用 `silentRefresh`，会替换当前列表。这会破坏推荐会话，需要在首页推荐场景停止自动替换。
- `ContentQueryService.getContentFactSnapshots` 的名称、注释与实际 SQL 不完全一致；当前 `selectBatchIds` 已过滤未过审、已删除内容。实现以 SQL 为准，不依据注释放宽可见性。

## 3. 产品行为

| 场景 | 推荐 | 热度 |
|---|---|---|
| 游客 | 热度主推荐＋近期探索＋游客曝光去重 | 现有统一热度流 |
| 登录，无行为/显式偏好 | 热度主推荐＋近期探索＋账号曝光去重 | 现有统一热度流 |
| 登录，有行为/显式偏好 | 原个性化算分＋近期探索＋账号曝光去重 | 现有统一热度流 |

曝光与下发是两个概念：服务器返回但未进入屏幕的帖子，不算曝光；同一浏览会话中已下发的帖子不再放入后续新页。请求失败重试仍可重放原页。

下拉刷新开启新会话，继续过滤24小时真实曝光；前一会话下发但未实际看见的帖子可以再次出现。切换分类开启新会话，但真实曝光在同一访客所有推荐分类间共享。热度页展示不写推荐曝光。

登录或退出改变推荐主体：首页立即作废旧请求、观察器及游标，开启新会话。游客曝光不自动合并到账号，保留原游客标识，退出后继续使用；本轮不做跨设备游客识别。

推荐场景不再每45秒替换列表，热度场景保留原定时逻辑；只在初次进入、主动刷新、切换分类/入口、身份变化、主动再看时开启新的推荐会话。返回首页继续本轮，过期提示刷新。

## 4. 实现默认值与边界

以下是工程默认值，不是另一次产品确认，可集中配置调整：

- 首页卡片与可用视口相交面积比例达到50%，记一次曝光；不额外引入停留时长判定。排除吸顶栏遮挡，页面隐藏、切换及旧请求期间不观察。
- 探索位按跨页累计每5条1条计算，小页仍能公平获得探索；每轮未补足的探索配额不在下一页翻倍补偿。
- 探索候选满足 `session.startedAt-7天 <= createTime <= session.startedAt`，从合格候选按会话随机种子抽取，考虑作者/标签多样性，不调用新模型。
- 显式厌恶沿用现有“强降权、不硬屏蔽”的约定：探索也优先非负偏好候选，不用探索位人为提拔负偏好帖子；没有合适候选就交还主推荐。
- 页面大小默认5，新协议最大20。旧热度协议不改变。
- 推荐会话闲置30分钟失效，最长存活2小时；同访客最多20个活跃会话，超过拒绝新建并明确返回429，不任意逐出正在翻页的会话。
- 曝光24小时逐条过期，用 Redis ZSET 的失效时间而非整个集合 TTL 表达。重复回传不延长同一条记录；过期后再次真实可见才开启新24小时。
- 初始保持双池各150，按300、600、1200扩召回。到窗口上限后，使用 MySQL 可见内容的时间键集分页补候选，避免将固定窗口耗尽误称全站耗尽。
- 单次扫描预算3000（Redis 两池读窗口分别计费，重叠窗口计入成本）；预算到顶且源未耗尽，返回 `SEARCHING` 和继续游标，不返回“看完了”。查询错误返回错误，不当作空源。
- Redis 无法使用时，新会话/翻页/回传明确失败，前端保留旧列表并允许重试，不伪称具备去重。

## 5. 范围与发布

本轮覆盖 `demo0` 推荐读链、推荐曝光回传以及小程序首页和服务调用方。不修改详情登录限制、点赞收藏评论规则、画像行为权重、显式偏好事实/MQ、Bot、管理端、热度公式、榜单版本化。

会话与曝光是可丢弃的展示状态，不是兴趣行为事实，不写 MySQL、不新增 Outbox/Inbox。候选与可见性仍以 MySQL 为准。内容域新增只读查询口，feed 域不得直接访问内容 Mapper。

后端先发布加法协议并保留旧请求分支，再发布小程序。新客户端带会话字段使用新语义；无会话字段保留旧语义并明确不属于本次新体验验收。灰度开关关闭时，新客户端得到旧响应并回退到旧展示能力。

当前工作区有大量既有未提交修改，实施需逐文件核对并保留；本次已按授权实施推荐服务与小程序；保留其他任务修改，不提交、推送。

## 6. 验收口径

必须证明游客稳定分页、同页重试、逐条24小时曝光、推荐探索、窗口外召回、耗尽/再看、身份切换和可见性变化。热度不按曝光排除，旧响应字段兼容。

单元测试不能代替真实 Redis 的原子性与 TTL 证据；HTTP 成功不能代替首页实际滚动曝光证据。设备验证、真实依赖阻塞分别记录。排行榜五分钟版本属于后续计划，不标为已实施。
