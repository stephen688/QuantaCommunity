## 2. 现状事实（已核对代码，实施时直接引用）

1. `recommend()`（`ContentServiceImpl` L326-455）只认 latest/hot；匿名可访问（`BaseContext.getCurrentId()` 可为 null）。
2. 曝光去重现状**只对 hot 生效**：`getExposedContentIds`/`saveExposedSet`（L1674-1703）对非 hot 直接返回空集；key=`recommend:exposed:{userId}`，TTL 24h，超 1000 条 pop 100。本计划将该机制**整体挪给画像流**，key 不变。
3. 现有 7 种 MQ 消息均无 userId 维度的行为事件；`HotScoreMessage` 只有 contentId+triggerType，不可复用。
4. `recordBrowseHistory`（L1507-1522）直接写 MySQL，best-effort；`BrowseHistory` 表有自增 id / browseDate / updateTime，支持增量扫描。
5. Outbox 挂法标杆：`likeContent`（L722-744）在事务内调 `outboxEventService.createHotScoreRecalculateEvent(...)`；新增行为事件沿用同一模式。
6. MQ 惯例：每个业务一套 `QUEUE/EXCHANGE/ROUTING_KEY` + RETRY + DLX 三件套（`RabbitMQConfig`）。
7. 定时任务惯例：Service Impl 上 `@Scheduled(cron = "${...}")`，cron 从配置读（`OutboxMaintenanceService` 模板）。
8. 现有热度公式在 HotScore 消费链路内（`like*3 + comment*2 + collect*5` / `(ageHours+2)^1.5`）；画像流重排需将其提为可复用方法。
9. latest 池 ZSET score=发布时间戳，hot 池 score=热度分——**两池 score 语义不同**，重排排序分一律 Java 现算，不读 ZSET score。
10. `RecommendProperties` 前缀 `quanta.recommend`（`@Data @Component @Validated`），扩嵌套类即可。
11. `ContentServiceImpl` 已 1983 行，重排逻辑**必须新建 Service**，不在其中继续堆码。

## 4. 全局约束

- **契约不变量**：HTTP 路径、`Result` 包装、`ScrollResult` 字段名不变；`ContentVO` 不变；权限语义（recommend 匿名可访问）不变。唯一契约变化：`scene=latest` 的返回语义（时间序 → 画像流/热度兜底）与画像流游标语义（`minScore/offset` 忽略入参、出参 `minScore=null, offset=0`）——这是 D8 既定决策，同步改 P4-01。
- **MySQL 是事实源**：画像 Hash 是派生快照；帖子的审核/删除状态以数据库为准，画像累加前校验（已删/驳回帖不累加）。
- **Outbox 铁律**：业务写与 Outbox 插入同一事务（项目既有模式）；消费者走 Inbox 幂等（consumerName+eventId）；事件带稳定 eventId（浏览对账 eventId=`user.behavior.browse:{browseHistoryId}`）。
- **测试策略（用户既定：粗粒度节拍）**：采用 **Task 级 TDD**——每个 Task 先集中写完该 Task 全部目标测试并确认 RED（因预期原因失败），再一次性实现到 GREEN；**不做函数级微节拍**，不为每个小函数单独立测试轮。每个 Task 收尾跑一次定向验证，每个分计划收尾跑一次模块级验证（定向测试集合 + `mvn -DskipTests compile`）。禁止删/跳/放宽既有测试。
- **风格**：新类沿用 `@RequiredArgsConstructor + private final`（构造期构建实例除外）；新增类必须有文件头注释（模块名+职责+边界），公开方法 Javadoc；核心步骤行内注释（中文注释、英文标识符）。
- **秘密不进仓库**；性能数字不编造；`RESULTS.md` 只写真实执行结果。

## 5. 最终验收门禁（全部门禁满足才算完成）

1. `mvn test` 全绿（无关既有失败可记录为证据充分的 PARTIAL/BLOCKED）。
2. 行为链路证据：点赞/收藏/评论各执行一次 → 画像 Hash 对应 field 与 `__total` 按 2/3/4 权重累加；取消赞/取消收藏不回滚（D9）。
3. 浏览对账证据：插入 browse_history 行 → 手动触发/等待对账任务 → 画像累加权重 1.0；重复运行同批不重复累加（Inbox 幂等）。
4. 衰减证据：手动触发衰减任务 → 全部 field ×0.95，低于 0.5 的 field 被删除；多实例并发只跑一次（锁生效）。
5. 画像流证据：构造两个画像不同的用户 → 同一时刻拉 `scene=recommend` 返回顺序不同；新用户/匿名 → 返回热度序且与 `scene=hot` 一致（α=1）；已曝光内容不再出现（隐式游标生效），池子耗尽 `hasMore=false`。
6. hot 流证据：连续拉取 `scene=hot` 不再写曝光 set，"滤光降级重拉"代码已删除；行为与删除前对同一数据集排序一致（除曝光过滤差异）。
7. P4-01 等 recommend 相关回归用例按新语义更新并通过。
8. 独立审查（`requesting-code-review` 流程）无未解决 Critical/Important 问题。
