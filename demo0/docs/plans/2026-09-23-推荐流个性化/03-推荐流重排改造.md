## Task 3.2 RecommendRerankService —— 画像流核心

**Files:**
- Create: `src/main/java/com/quanta/demo0/service/RecommendRerankService.java`
- Create: `src/main/java/com/quanta/demo0/service/Impl/RecommendRerankServiceImpl.java`
- Test: `src/test/java/com/quanta/demo0/service/Impl/RecommendRerankServiceImplTest.java`

**接口（固定）：**

```java
public interface RecommendRerankService {

    /**
     * 画像流重排：召回 → 曝光过滤 → 归一化算分 → 排序截页 → 回写曝光。
     * 匿名用户走 α=1 纯热度（不读不写曝光）。游标入参忽略（曝光 set 为隐式游标）。
     *
     * @return list 为当页内容；hasMore = 过滤曝光后候选是否还有剩余
     */
    RerankResult rerank(Long userId, Integer contentType, int pageSize);
}
```

`RerankResult`（新建 vo 或内部 record）：`List<Content> contents`（保持推荐序）、`boolean hasMore`。**VO 组装复用 `ContentServiceImpl` 现有装配（作者/点赞高亮），本 Service 不碰 VO**——返回 Content 列表，由 recommend() 现有第 8~11 步装配。

**实现流程（固定，逐步行内注释）：**

1. **召回**：`ZREVRANGE` hot 池 top `recallHotSize` + latest 池 top `recallLatestSize`（池名复用现有 `resolveRecommendHotKey` / `resolveRecommendKey` 的 key 规则，contentType 分类池支持保持）；两池按 contentId 去重合并（hot 优先保留）。**不读 ZSET score**（latest 池 score 是时间戳，语义不同——总览 §2.9）。
2. **曝光过滤**（仅登录用户）：`SMEMBERS recommend:exposed:{userId}` 剔除已曝光。
3. **查帖子**：`selectBatchIds`；过滤非审核通过/已删除（以 MySQL 为准，兜底 ZSET 时差）。
4. **读画像**：`userProfileService.getProfile(userId)`（匿名传 null 时跳过）。
5. **算分**（核心，独立私有方法便于单测）：
   - 热度分：对每个候选 Content 用现有公式 `liked*3 + commentCount*2 + collectCount*5 / (ageHours+2)^1.5` **Java 现算**——公式从 HotScore 消费链路提取为静态工具方法（如 `HotScoreCalculator.calculate(Content)`，原调用点改引此方法，行为不变），**不得复制公式**。
   - 归一化：候选集内 min-max，最热=1.0（单候选时=1.0）。
   - 匹配分：`resolveContentTags(content)` 与画像 field 交集的权重和 ÷ 画像标签总权重（不含 `__total`），归一到 [0,1]；无画像/无交集=0。
   - α 过渡：`S = min(1, __total / behaviorSaturateThreshold)`（无画像 S=0）；`α = 1 - S·(1-alphaMin)`；`finalScore = α·normHot + (1-α)·matchScore`。γ 项（显式偏好）**预留参数位但不实现**（④阶段接入）。
6. **排序截断**：finalScore 降序（分数相同按 contentId 降序，稳定排序），截 `pageSize`。
7. **回写曝光**（仅登录用户）：沿用现有 `saveExposedSet` 语义写 `recommend:exposed:{userId}`（**迁移该方法或提取公共逻辑**——03 Task 3.3 处理归属，本 Task 先以注入方式调用 ContentServiceImpl 中暴露的既有逻辑或复制提取，实施时以最小改动为准并在交付摘要说明）。
8. `hasMore` = 过滤曝光后候选数 > pageSize。

**测试目标（一次写完，先 RED；mock Redis/Mapper/ProfileService）：**
- 召回合并去重（两池同帖只留一份）。
- 曝光过滤剔除已曝光 id。
- 非审核通过帖被过滤。
- 热度归一化：构造 3 候选不同计数，断言最热=1.0、最低=0。
- 匹配分：画像 {life:8, professional:2}，life 帖 matchScore=0.8。
- α 过渡：`__total=0` → 顺序=纯热度；`__total≥阈值` → α=alphaMin、画像主导（构造 life 画像用户，life 低热帖排到 professional 高热帖前）。
- 排序稳定性、截断、hasMore 边界（候选=pageSize 时 hasMore=false）。
- 匿名：不读画像、不读写曝光、返回热度序。
