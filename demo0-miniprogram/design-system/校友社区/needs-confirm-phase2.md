# 第二阶段需产品确认的大改建议

> 本文件收纳第二阶段设计过程中发现的「新增功能、改变主流程、调整信息架构、需要接口或数据模型支持」的建议。  
> 已确认采纳的条目会在原编号下标注状态，并同步进入默认设计稿和前端优先级；未标注已确认的条目不得当作默认实现项。

---

## 1. 确认原则

### 1.1 什么进入本文件

| 类型 | 判断标准 |
|------|----------|
| 新功能 | 当前页面没有入口、路由、接口或数据字段支撑 |
| 主流程变化 | 会改变搜索、发布、详情阅读、资料编辑、用户主页等核心路径 |
| 信息架构调整 | 会新增 tab、分组、批量管理、二级导航或重排页面主区块 |
| 数据模型变化 | 需要后端新增字段、枚举、推荐逻辑、权限或分页能力 |
| 运营依赖 | 需要运营配置、活动内容、推荐池或人工审核策略 |

### 1.2 默认设计稿可直接做的边界

- Token、色彩、字号、圆角、描边、空/错/加载状态统一。
- 现有组件的样式升级，例如 `content-card`、`state-block`、`page-list-footer`、`search-input-bar`。
- 不新增字段的文案、触摸态、禁用态、加载态、错误态补齐。
- 使用现有路由的入口视觉强化，例如首页搜索框跳转搜索页、详情页进入已有发布回答页。

### 1.3 已确认纳入本轮的条目

| 原编号 | 条目 | 纳入方式 |
|--------|------|----------|
| 2.1 | 搜索页新增热门搜索 / 热门校友推荐 | 进入 `secondary-pages/search.md` 搜索页默认信息区块，作为搜索历史下方的轻量推荐模块 |
| 3.1 | 详情页评论分层 / 楼中楼 | 进入 `secondary-pages/detail.md` 评论区默认设计，采用后端不改、前端展开时加载回复列表的方案 |
| 3.3 | 专业详情回答采纳 / 最佳回答流程 | 进入 `secondary-pages/detail.md` 专业详情与回答详情设计稿，补充采纳操作、权限态和状态同步验收 |

## 2. 搜索组

### 2.1 搜索页新增热门搜索 / 热门校友推荐

**状态：已确认，纳入本轮正式设计稿。**

- **涉及页面**：`pages/search/index`
- **变更范围**：在搜索历史下方新增热门关键词、热门校友、热门问题推荐模块。
- **潜在收益**：缓解空历史冷启动，增强社区活跃感。
- **实现边界**：默认采用轻量推荐模块，优先展示热门关键词 + 热门问题；热门校友仅在已有用户推荐数据时显示。
- **实现风险**：需要推荐数据源、运营排序或后端热度统计；模块必须控制高度，避免搜索页变成「推荐广场」。
- **接口/数据依赖**：热门关键词列表、推荐用户列表、推荐内容列表、点击埋点可选。
- **建议结论**：纳入本轮，详见 `secondary-pages/search.md` 与 `implementation-priority-phase2.md`。

### 2.2 搜索输入联想 / 自动补全

- **涉及页面**：`pages/search/index`、`components/search-input-bar`
- **变更范围**：用户输入时展示联想词、用户或内容建议。
- **潜在收益**：提升搜索效率，降低错词无结果概率。
- **实现风险**：需要防抖、接口性能、键盘遮挡、空态切换；小程序端输入体验容易变复杂。
- **接口/数据依赖**：联想词接口、最小输入长度、分页或数量限制。
- **建议结论**：不纳入默认稿。优先保持历史 chip + 结果页无结果引导。

### 2.3 AI 摘要赞踩、重新生成、反馈原因

- **涉及页面**：`pages/search-result/index`、`pages/search-ai-detail/index`
- **变更范围**：AI 摘要卡和 AI 详情页新增赞/踩、重新生成、反馈原因入口。
- **潜在收益**：形成 AI 内容质量反馈闭环。
- **实现风险**：当前设计稿只把 AI 摘要作为结果辅助，不承诺生成控制；增加反馈会强化 AI 功能预期。
- **接口/数据依赖**：反馈提交、重新生成任务、生成状态轮询、失败重试策略。
- **建议结论**：暂不纳入本轮。若产品后续明确 AI 搜索为核心能力，再扩展。

### 2.4 搜索结果高级筛选

- **涉及页面**：`pages/search-result/index`
- **变更范围**：新增按院系、年份、作者、时间排序等筛选。
- **潜在收益**：专业问题或校友查找更精准。
- **实现风险**：改变结果页信息架构，筛选状态与分页、空态、URL 参数都要重做。
- **接口/数据依赖**：筛选字段、排序字段、后端搜索参数支持。
- **建议结论**：本轮不采用，仅保留现有内容类型 tabs。

## 3. 内容详情组

### 3.1 详情页评论分层 / 楼中楼

**状态：已确认，纳入本轮正式设计稿。**

- **涉及页面**：`pages/detail-life/index`、`pages/answer-detail/index`（专业详情页无评论区，不在此列）
- **变更范围**：评论从平铺列表升级为二级回复、展开更多、被回复人展示。
- **潜在收益**：讨论关系更清晰，适合高互动内容。
- **实现边界**：后端代码不改；前端先调用一级评论列表，再在用户点击「展开回复」时按 `parentCommentId + contentId/answerId` 调用回复列表接口，并把回复挂到对应一级评论下方。
- **前端工作量**：需要补充每条评论的 `replyLoading`、`replyLoaded`、`replyLoadError`、`expanded` 状态，以及回复列表插入、失败重试、回复目标定位和收起/展开交互。
- **实现风险**：前端状态复杂度上升；展开时二次请求可能有延迟，需要 loading、失败重试和防重复点击。
- **接口/数据依赖**：复用现有一级评论列表与回复列表能力，不新增后端接口、不改后端数据模型。
- **建议结论**：纳入本轮，详见 `secondary-pages/detail.md` 与 `implementation-priority-phase2.md`。

### 3.2 详情页新增相关推荐

- **涉及页面**：`pages/detail-life/index`、`pages/detail-pro/index`、`pages/answer-detail/index`
- **变更范围**：正文或评论后新增「相关内容」「同院系在聊」推荐卡。
- **潜在收益**：提升内容消费深度。
- **实现风险**：会拉长详情页，可能削弱评论/回答入口；推荐质量不足会显得模板化。
- **接口/数据依赖**：相关推荐接口、去重规则、内容类型混排策略。
- **建议结论**：不纳入本轮。若后续要提升停留时长，可在详情底部做 A/B 方案。

### 3.3 专业详情回答采纳 / 最佳回答流程

**状态：已确认，纳入本轮正式设计稿。**

- **涉及页面**：`pages/detail-pro/index`、`pages/answer-detail/index`
- **变更范围**：问题作者可采纳回答，回答卡展示更强「最佳回答」状态。
- **潜在收益**：专业问答更闭环，优质回答更突出。
- **实现边界**：采纳操作只对问题作者开放；回答卡展示「最佳回答/已采纳」状态；是否允许撤销由接口能力决定，默认设计保留二次确认。
- **实现风险**：需要权限校验、状态同步、撤销采纳规则；会影响回答排序和详情状态。
- **接口/数据依赖**：采纳接口、回答状态字段、问题作者权限。
- **建议结论**：纳入本轮，详见 `secondary-pages/detail.md` 与 `implementation-priority-phase2.md`。

### 3.4 图片画廊 / 长图浏览模式

- **涉及页面**：`pages/detail-life/index`、`pages/detail-pro/index`
- **变更范围**：从普通图片预览升级为自定义画廊、图片计数、长按菜单。
- **潜在收益**：图文内容浏览体验更完整。
- **实现风险**：微信原生 `previewImage` 已覆盖基础需求，自定义画廊会增加维护成本。
- **接口/数据依赖**：无强接口依赖，但需要更多前端状态。
- **建议结论**：不纳入本轮。继续使用现有预览能力和暖色占位。

## 4. 发布 / 编辑组

### 4.1 发布回答增加草稿箱

- **涉及页面**：`pages/publish-answer/index`
- **变更范围**：离开页面时保存草稿，再次进入可恢复。
- **潜在收益**：长回答场景更安全，减少误退出损失。
- **实现风险**：需要草稿生命周期、问题 ID 绑定、提交后清理、隐私边界。
- **接口/数据依赖**：可本地缓存起步；多端同步则需要后端草稿接口。
- **建议结论**：暂不纳入默认稿。当前只确保提交 loading、失败恢复、字数警告清晰。

### 4.2 发布回答支持图片 / 附件

- **涉及页面**：`pages/publish-answer/index`
- **变更范围**：回答编辑卡增加图片上传或附件上传。
- **潜在收益**：专业问答可补充截图、资料或说明。
- **实现风险**：会改变回答数据结构，也增加审核和展示复杂度。
- **接口/数据依赖**：回答图片字段、上传接口、详情展示适配、审核规则。
- **建议结论**：不纳入本轮，除非后端已支持回答媒体。

### 4.3 资料编辑新增完整个人资料字段

- **涉及页面**：`pages/profile-edit/index`
- **变更范围**：在昵称/头像/认证之外新增 bio、联系方式、专业方向、公司、城市等字段。
- **潜在收益**：用户主页可信度和校友连接效率提升。
- **实现风险**：表单变长，隐私和审核要求提高；资料完整度规则也要重算。
- **接口/数据依赖**：用户资料字段、隐私可见性、保存接口、资料完整度规则。
- **建议结论**：暂不纳入本轮。当前只美化已有资料与认证表单。

### 4.4 认证流程拆成多步骤

- **涉及页面**：`pages/profile-edit/index`
- **变更范围**：将身份选择、基本信息、提交确认拆成步骤式流程。
- **潜在收益**：认证字段增多时更清晰。
- **实现风险**：当前认证字段有限，多步骤会增加操作成本。
- **接口/数据依赖**：无新增字段也能做，但需要保存中间状态。
- **建议结论**：本轮不采用，保持单页表单。

## 5. 个人内容组

### 5.1 我的收藏新增文件夹 / 分类管理

- **涉及页面**：`pages/my-collect/index`
- **变更范围**：收藏内容支持文件夹、标签、筛选或移动收藏。
- **潜在收益**：收藏较多时更容易回看。
- **实现风险**：从简单列表变为资产管理工具，交互和空态复杂度明显提升。
- **接口/数据依赖**：收藏夹模型、创建/重命名/删除、移动内容、筛选查询。
- **建议结论**：不纳入本轮。当前只做收藏列表样式和空态文案。

### 5.2 我的发布支持批量管理

- **涉及页面**：`pages/my-content/index`
- **变更范围**：新增多选、批量删除、批量隐藏或批量重新提交。
- **潜在收益**：内容量大时管理效率更高。
- **实现风险**：权限、撤销、删除确认、审核状态冲突都需要设计。
- **接口/数据依赖**：批量操作接口、内容权限、失败部分回滚策略。
- **建议结论**：不纳入本轮。保留审核状态筛选即可。

### 5.3 浏览历史按日期分组

- **涉及页面**：`pages/browse-history/index`
- **变更范围**：列表从平铺改为「今天 / 昨天 / 更早」分组。
- **潜在收益**：历史内容更好回忆和定位。
- **实现风险**：改变列表结构，需要处理分组标题、分页跨天、清空局部日期等问题。
- **接口/数据依赖**：浏览时间字段必须稳定；可前端分组但分页边界需验证。
- **建议结论**：可作为 P2 候选，但不纳入本轮默认稿。

### 5.4 点赞 / 收藏 / 历史页增加筛选 tabs

- **涉及页面**：`pages/my-liked/index`、`pages/my-collect/index`、`pages/browse-history/index`
- **变更范围**：新增生活/专业、时间、作者等筛选。
- **潜在收益**：资产列表更可控。
- **实现风险**：四个页面需要统一筛选模型，且与搜索结果筛选重复。
- **接口/数据依赖**：列表接口支持筛选参数。
- **建议结论**：不纳入本轮。内容类型展示由卡片标签承担。

## 6. 用户主页

### 6.1 用户主页新增私信入口

- **涉及页面**：`pages/user-profile/index`
- **变更范围**：关注按钮旁增加「私信」或「发消息」入口。
- **潜在收益**：校友之间连接更直接。
- **实现风险**：涉及即时消息、隐私、防骚扰和未关注可见性规则。
- **接口/数据依赖**：私信路由、会话模型、消息接口、权限策略、举报/拉黑可选。
- **建议结论**：不纳入本轮默认稿。当前 hero 操作区只保留编辑资料/关注/已关注。

### 6.2 用户主页内容分区 tabs

- **涉及页面**：`pages/user-profile/index`
- **变更范围**：新增「发布 / 回答 / 收藏 / 互动」等分区。
- **潜在收益**：公开内容更完整，能体现用户贡献。
- **实现风险**：改变主页信息架构，并引入隐私边界。
- **接口/数据依赖**：公开回答、公开收藏、公开互动列表接口与隐私设置。
- **建议结论**：不纳入本轮。只展示当前已有公开发布列表。

### 6.3 关注者 / 粉丝列表可点击

- **涉及页面**：`pages/user-profile/index`
- **变更范围**：统计区数字变成入口，进入关注者或粉丝列表。
- **潜在收益**：社交关系更可探索。
- **实现风险**：新增路由和列表页；需要处理隐私、分页和空态。
- **接口/数据依赖**：关注者列表、粉丝列表、关注状态批量查询。
- **建议结论**：本轮统计只作为展示，不做入口。

### 6.4 个人动态时间线

- **涉及页面**：`pages/user-profile/index`
- **变更范围**：把发布内容、回答、点赞等混合成动态流。
- **潜在收益**：主页更像完整社区档案。
- **实现风险**：与「TA 的发布」重复，且会显著改变页面定位。
- **接口/数据依赖**：动态聚合接口、隐私规则、内容类型渲染。
- **建议结论**：不纳入本轮。

## 7. 全局导航与跨页面能力

### 7.1 新增搜索 Tab 或活动 Tab

- **涉及页面**：`miniprogram/app.json`、`custom-tab-bar/index`
- **变更范围**：把搜索或活动提升为一级入口，调整当前 4 tab + 发布入口结构。
- **潜在收益**：强化搜索或运营活动曝光。
- **实现风险**：影响全局导航习惯，需要重新定义一级页面职责。
- **接口/数据依赖**：如新增活动 tab，需要活动列表接口。
- **建议结论**：不纳入本轮。继续沿用既有 TabBar 信息架构。

### 7.2 全局通知红点规则重构

- **涉及页面**：`custom-tab-bar/index`、`pages/notification/index`、其他产生通知的页面
- **变更范围**：细分系统/互动/私信红点，或按类型展示不同 badge。
- **潜在收益**：消息来源更清楚。
- **实现风险**：当前消息页仍是单列表，红点细分会提前暴露未实现分类。
- **接口/数据依赖**：按类型未读数接口、消息类型枚举稳定。
- **建议结论**：不纳入本轮。保持一个总未读 badge。

### 7.3 新增全局举报 / 拉黑能力

- **涉及页面**：详情页、评论、用户主页
- **变更范围**：在内容、评论、用户菜单中加入举报、拉黑、屏蔽。
- **潜在收益**：社区治理更完整。
- **实现风险**：需要审核流、证据留存、用户限制策略和客服后台。
- **接口/数据依赖**：举报接口、原因枚举、拉黑关系、后台处理状态。
- **建议结论**：作为社区治理专题规划，不纳入本轮 UI 美化。

## 8. 建议确认顺序

| 优先确认 | 建议 | 原因 |
|----------|------|------|
| 1 | AI 摘要赞踩 / 重新生成 | 如果 AI 搜索是产品重点，需要尽早定交互和接口 |
| 2 | 用户主页私信入口 | 影响用户关系链和后续消息体系 |
| 3 | 资料字段扩展 | 影响资料完整度、用户主页和认证边界 |
| 4 | 收藏夹 / 批量管理 | 偏资产管理，可后置 |

## 9. 本轮明确不阻塞的事项

- `needs-confirm-phase2.md` 中未标注已确认的建议，不影响 `implementation-priority-phase2.md` 的 P0/P1 样式落地。
- 二级页默认设计稿继续遵循：不重排全局导航；已确认的 2.1、3.1、3.3 按对应页面设计稿实施。
- 若产品只确认其中单项，应单独回写到对应页面设计稿和优先级文档，避免一次性扩大范围。
