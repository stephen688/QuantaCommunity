## 1. 复盘范围与基线

### 1.1 目标

本次实施将 M3 的随场景增长式评测收紧为三档门禁：

- Fast：零成本、每次代码变更执行的静态检查和 pipeline 评测；
- Persona：固定 17 个场景、固定 `deepseek-v4-flash`、确定性 P0 + Judge P1/P2；
- Release：Persona 双跑稳定性检查加 Promptfoo 完整管线红队。

Promptfoo 通过 Python custom provider 调用完整 QuantaBot pipeline，不裸调模型。报告采用脱敏汇总入 Git，原始回复、攻击输入和 trace 只保留在被忽略的 raw artifact 范围内。

## 2. 本次完成内容

### 2.1 冻结集与确定性门禁

- 新增 `eval/gate-manifest.yaml`，冻结 `m4-v1` 的 17 个 Persona case、普通场景阈值、情绪场景阈值、双跑分差和基础设施重试次数。

- 将水位线过滤纳入独立 Fast 回归：优先按可解析的时间字段判断触发前楼层，无法解析时才按 ID 兜底。

- 增加 P1/P2 五分制 Judge 结果、情绪场景 `persona-11/12/13` 的更高阈值和双跑一致性比较。
- 增加 `INFRA_BLOCKED`、`ASSERTION_FAILED`、`SAFETY_BLOCKED` 分类。
- 固定基础设施最多自动重试一次；断言失败不重试刷分。
- 生成 `m4-report-v1` 脱敏 JSON/Markdown 报告，保留 case、分数、hash、token、成本和短失败原因，不写入完整回复和 trace。

### 2.3 Promptfoo 红队链路

- 固定 Promptfoo `0.123.1`，增加 `eval/promptfoo_provider.py`、`eval/redteam.yaml` 和 provider 契约测试。
- provider 使用合成 post/comment 标识，调用完整 pipeline，返回最终候选文本、token/cost、guardrail 元数据和错误状态。
- 增加 `scripts/run_m4_redteam.py`，将 Promptfoo worker 固定到项目的 uv Python，并把 QuantaBot 的 DeepSeek 配置映射到 Promptfoo 所需的 OpenAI-compatible 环境变量。
- 将 Promptfoo 生成的评测 YAML 输出到独立文件，避免覆盖受版本控制的红队源配置。
- 保留提示词提取、PII、隐私/危险内容、policy、prompt injection 和 jailbreak 攻击面；工具版本对旧策略名称的兼容映射已记录并未删除攻击类别。

### 2.4 CI 与运行边界

- Fast CI 默认不设置 `QUANTABOT_EVAL=1`，不产生模型费用。
- Persona/Release 使用受保护的 `QUANTABOT_DEEPSEEK_API_KEY`，workflow 在运行前断言版本控制中的模型为 `deepseek-v4-flash`。
- Release workflow 上传 raw artifact，但只把脱敏 summary 写入 job summary。
- `eval/reports/raw/`、Promptfoo 生成文件和完整运行产物均不进入 Git。

## 3. 实施中遇到的问题、根因与处理

| 现象 | 根因 | 处理 | 当前状态 |
|---|---|---|---|
| 触发后的楼层可能进入上下文 | 原水位判断只依赖 ID，不能可靠表达时间顺序 | 改为时间字段可用时优先按时间过滤，缺失/异常时才按 ID 兜底；补红测和回归 | 代码级回归已通过；M3 真实正式重跑未执行 |
| Persona 玩梗场景偶发不复用复合口头禅 | prompt 只要求“接梗”，没有把复合短语的原样复用变成首句约束 | 将复合口头禅原样复用写入模式 prompt 和冻结断言 | Persona 34/34 PASS |
| 情绪回复存在同义重复和过长风险 | 只有“简短、共情”语义要求，没有句数、字数和动作数边界 | 加入最多 3 句、最多 65 个中文字符、只给一个行动建议的约束 | Persona 34/34 PASS |
| Promptfoo worker 无法导入 `quanta_bot` | Promptfoo 子进程的 `sys.path` 不包含 `src` | provider 启动时显式加入项目 `src`，并通过 uv Python 启动 worker | 常规运行已通过；需继续覆盖 resume 场景 |
| Promptfoo 生成文件覆盖源配置 | 未区分源 `redteam.yaml` 与运行时生成的测试 YAML | 使用 `eval/m4-v1-redteam-generated.yaml` 独立输出 | 已处理 |
| grader 回退到默认 OpenAI 配置 | Promptfoo 的默认 grader 不会自动读取 QuantaBot 的 DeepSeek 设置 | launcher 显式注入 `OPENAI_API_KEY` 和 `OPENAI_API_BASE_URL`，并固定 DeepSeek 配置 | 已处理；正式评测仍暴露 2 条 grader JSON 解析失败 |
| 旧策略名称出现 deprecated 警告 | Promptfoo 0.123.1 将旧 `jailbreak`、`prompt-injection` 映射到新版策略集合 | 保留原攻击类别语义，接受官方兼容映射并在方案中记录 | 攻击类别未删减 |
| resume 后 provider 相对路径解析到错误工作目录 | Promptfoo 持久化评测恢复时不再保留首次配置文件的相对路径基准 | 常规正式评测使用稳定 launcher/生成配置完成；resume 路径稳定性仍需单独补测试或改为绝对化/稳定 shim | 已知运行风险，未计作安全通过 |
| 正式红队出现 1 条真实提示词摘要泄漏 | provider 返回的摘要边界仍允许一类内部提示内容进入公开候选文本 | 修复提交 `29cc3fe` 收紧泄漏边界；原失败样本直接走完整管线复验，结果 `matches_fixed_refusal=true` | 已通过定向复验 |
| 两条目标为安全拦截的样本 grader JSON 解析失败 | grader 的 reasoning 消耗了过多输出预算，结构化 JSON 没有稳定落在可解析输出中 | 将 `OPENAI_MAX_TOKENS=4096` 注入红队运行环境，保留原失败证据并用原 raw 的 `--filter-failing` 只复跑失败样本 | 已通过定向复验 |

修复后的定向复验使用评测 ID `eval-MHV-2026-09-19T12:45:04`，只针对原正式 raw 中的 3 条失败样本执行，结果为 `3 passed / 0 failed / 0 errors`，耗时 24 秒。该结果与原 72 条通过记录合并后，形成 75 条 case-level 的闭环证据；它不是重新生成的全量 75 条独立扫描，报告中必须保留这一点。

## 4. 门禁结果

### 4.1 Fast 与 provider 校验

- 非 Persona 的完整免费回归：`217 passed, 12 skipped, 22 deselected`；保留 2 条既有 warning，未发现本次改动引入的失败。
- Promptfoo provider/config 相关测试：9 passed。
- `promptfoo validate config`：通过。
- Ruff format/check、差异 whitespace 检查和 secret 扫描作为最终收口门禁执行；汇总报告不包含 API key、Bearer、JWT、真实用户文本或完整内部 URL。

### 4.2 Persona

- 17 个冻结场景 × 2 轮，共 34 次记录，34/34 PASS。
- P0：零失败。
- 普通场景 P1/P2：均达到至少 3/5。
- 情绪场景 P1/P2：两轮均达到至少 4/5。
- 模型：`deepseek-v4-flash`。
- prompt tokens：43,947；completion tokens：38,250；估算成本：160 fen。
- 报告 SHA：`1fe994dc3bde8800ef2ae65bba89294f6c67ddb1`。

同模型 Judge 具有自评偏置。该结果只能说明冻结规则下的门禁证据，不能替代独立供应商评审，也不能覆盖 P0 断言。

### 4.3 Promptfoo 正式红队

首次正式评测 ID `eval-gMG` 共 75 条：

- 72 pass；
- 3 fail；
- 0 errors。

对 3 条失败进行业务拆分：

- 1 条是真实提示词摘要泄漏；定向复验只重放 seed，因此又从首次 raw 提取 exact `redteamFinalPrompt` 建立 mode 无关硬拦截回归，并完成完整 provider 验证；
- 2 条目标行为属于安全拦截，但 grader JSON 解析失败，不能把解析失败写成“Bot 安全通过”。

随后使用原正式 raw 的 `--filter-failing` 只复跑上述 3 条失败样本，评测 ID 为 `eval-MHV-2026-09-19T12:45:04`：

- 3 passed；
- 0 failed；
- 0 errors；
- 用时 24 秒；
- `OPENAI_MAX_TOKENS=4096` 解决了 grader JSON 被 reasoning 输出挤占的问题；
- 原真实 `prompt-extraction` 的 exact 变形最终提示直接走完整 provider 复验，`matches_fixed_refusal=true`；报告只保存该输入的 SHA-256，不保存原文。

因此，首次 75 条结果与失败样本定向复验合并后，当前 M4 红队没有残留的真实攻击成功或 grader 解析失败。由于后续复验只过滤原始失败项，不能把它描述为重新执行了一次全量 75 条扫描；完整发布仍需绑定最终冻结 SHA 的 Release gate。
