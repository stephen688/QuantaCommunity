# M5-演练与上线终验 实施计划（M5 计划 4/4）

> **For agentic workers:** 本计划按 AGENTS.md §6 工作流执行。git 命令在 `QuantaCommunity` 根仓库执行，路径带 `QuantaBot/` 前缀。本文件为运维/验收型计划：**零生产代码改动**（演练若暴露缺陷 → 按 TDD 单独修复 commit，先补测试再修）。
> **前置依赖**：前三份 M5 计划全部合入 main。

**Goal:** 三场全真栈演练（kill switch 置位止血 / 灰度放量与记忆版本隔离 / 成本打满分档）+ 对账与指标演练留证 + PRD 上线前置四条件终验（最终冻结 SHA 复跑 Release gate 含红队），M5 达到可上线状态并回写全部文档。

**Architecture:** 演练环境=本地全真栈（同 M3 轨道 A 口径：demo0 Java 主服务 + QuantaBot compose 十容器栈，评论机审开启）；演练动作=向 agent-redis 写控制面/成本键 + 经 demo0 发真实 @ 评论；证据=决策日志（SQLite）+ Langfuse trace + 时间线文档落 `eval/reports/`。终验=四条件逐项可执行验收，第 4 项评测回归绑定最终 SHA 复跑 M4 三档门禁。

**Tech Stack:** docker compose / redis-cli / demo0 api-test 操作口径（`demo0/docs/api-test/`，不改 demo0 代码）/ M4 门禁脚本。

**Spec:** `总计划.md` §2 M5 节验收标准 5 条 + §4 汇总表终验列 + PRD §8 上线前置四条件。grill 共识落地第 10/16 条。

## Global Constraints

- 同计划 1 的 Global Constraints 全文适用。
- 演练在**本地全真栈**执行（demo0 侧写库与机审开启）；不碰任何生产数据。
- kill 键值只认字符串 `"true"`（M2 契约）；成本演练使用当天真实成本键但必须保存原值与 TTL，结束时恢复“原值 + 演练期间真实生成费用”，失败也走同一恢复路径，不得 `DEL` 或覆盖丢失当天数据。
- 证据必须可对质：每场演练记录时间线（UTC）+ decisions 表行数前后对比 + demo0 comment_id + Langfuse trace 线索；不口报"应该生效"。
- Release gate 复跑产生真实费用（Persona 双轮 17×2 真调 + 红队 75 样本；M4 参考时长 1h24m）——执行前向管理员确认时点。
- 红队复跑前检查 Promptfoo resume 路径稳定性（AGENTS §6.5 观察清单）。

### Task 1: kill switch 置位止血演练（总计划验收①）

**Files:**
- Create: `QuantaBot/eval/reports/m5-drill-killswitch.md`（演练证据，唯一新增文件）

- [ ] **Step 1: 基线——置位前正常回复链路**

1. 记录当前 UTC 时刻 `T_base` 与 SQLite 决策行数：
   `uv run --project QuantaBot python -c "import sqlite3; print(sqlite3.connect('QuantaBot/data/decisions.db').execute('SELECT COUNT(*) FROM decisions').fetchone())"`
2. 经 demo0 发 1 条真实 @ 评论（沿用 `demo0/docs/api-test/` 操作口径）→ 等待回复落库 → 确认 demo0 帖子出现 1 条 AI 回复、SQLite 新增 1 行 `replied`、Langfuse 出现对应 trace。此为"置位前正常态"基线证据。

- [ ] **Step 2: 置位 kill 并验证止血（≤5s 生效 + 零新回复）**

1. 记 UTC 时刻 `T_kill`，置位：
   `docker exec <agent-redis 容器名> redis-cli SET quantabot:switch:kill "true"`（容器名以 `docker compose ps` 实测为准）
2. 立即（`T_kill` 后 10s 内）经 demo0 发 2 条 @ 评论。
3. 等待 60s，验证止血三件：
   - SQLite 决策行数与 `T_kill` 时一致（零新行）；
   - demo0 两帖均无 AI 回复；
   - app 容器日志无新 pipeline 处理记录：`docker logs <app 容器名> --since <T_kill相对时长>`。
4. （可选加分）若恰有在途消息撞上置位瞬间，SQLite 出现 `skipped_killswitch` 行——一并留档（管线侧短路证据；消费暂停为主证据，此项不强求）。

- [ ] **Step 3: 解除并验证恢复**

1. `redis-cli SET quantabot:switch:kill "false"`，记 `T_release`。
2. 被压住的 2 条消息在轮询周期（≤5s）后开始处理 → SQLite 新增 2 行（`replied` 或诚实决策）、demo0 出现对应回复。
3. 若解除后 60s 内无处理迹象 → 检查 RabbitMQ unacked（`docker exec <rabbitmq 容器名> rabbitmqctl list_queues name messages_unacknowledged`）——hold 消息应回到 ready 被消费。

- [ ] **Step 4: 落证据**

`eval/reports/m5-drill-killswitch.md` 模板：

```markdown
# M5 演练：kill switch 置位止血（总计划验收①）

- 日期/环境：<UTC 日期>；本地全真栈（demo0 + compose 十容器，机审开启）
- 时间线（UTC）：
  - T_base=<时刻>：基线回复 1 条（comment_id=<id>，decision=replied，trace=<Langfuse trace 链接或 id>）
  - T_kill=<时刻>：SET quantabot:switch:kill "true"
  - T_kill+10s 内发出 2 条 @（comment_id=<id1>, <id2>）
  - T_kill+60s 检查：decisions 行数 <置位前>→<置位前>（零新增）；demo0 零新 AI 回复；app 日志零新处理
  - T_release=<时刻>：SET kill "false"
  - T_release+60s 检查：decisions 新增 2 行（<decision1>, <decision2>）；demo0 回复可见
- 生效延迟：置位→消费暂停 ≤ 轮询间隔 5s（以 app 日志最后处理记录与 T_kill 差值佐证：<实测秒数>s）
- 结论：PASS/FAIL（FAIL 时按 §6.5 复盘流程处置）
```

### Task 2: 灰度放量 + 记忆版本隔离演练（总计划验收②）+ 成本打满分档演练（验收③）

**Files:**
- Create: `QuantaBot/eval/reports/m5-drill-graylist-memory-isolation.md`
- Create: `QuantaBot/eval/reports/m5-drill-cost-tier.md`

- [ ] **Step 1: 灰度放量演练**

1. 基线：清空灰度语义（`redis-cli DEL quantabot:switch:graylist`）→ 发 @（用户 U1）→ replied（全量态）。
2. 置白名单仅含另一用户 U2：`redis-cli SET quantabot:switch:graylist "[<U2 的 userId>]"`
3. 等 ≥5s（轮询生效）→ 用户 U1 发 @ → 验证：SQLite 新行 `decision=skipped_graylist`、demo0 无回复。
4. 用户 U2 发 @ → 验证：`replied`、回复可见（白名单放行）。
5. `redis-cli SET quantabot:switch:graylist "[]"` → U1 再发 @ → `replied`（空=全量恢复）。

- [ ] **Step 2: persona_version 远程键 + 记忆版本隔离演练（验收②）**

1. 基线：`redis-cli DEL quantabot:switch:persona_version` → 发 @（用户 U1，选会触发记忆写入的触发，如自述考研偏好）→ Langfuse trace `persona_version=<本地 hash>`（记为 `V_local`），若有 memory_ops ADD → Qdrant 记忆落在 `V_local` 版本。
2. 置远程版本：`redis-cli SET quantabot:switch:persona_version "v5-memory-isolation-drill"` → 等 ≥5s。该动作只切换记忆版本键，不加载旧 prompt，也不宣称旧 prompt 恢复。
3. 同用户再发 @ → 验证 trace `persona_version=v5-memory-isolation-drill`，且 `V_local` 版本的 `memory_selected_ids` 为空/召回为空——**旧版本记忆检索返回空（隔离生效，验收②判据）**；Langfuse metadata 可查。
4. 清空远程键：`redis-cli DEL quantabot:switch:persona_version`（或 SET 回 `V_local`）→ 等 ≥5s → 再发 @ → trace 回到 `persona_version=V_local`；分别核对两个版本的 payload 过滤，证明版本边界仍隔离。这里不恢复旧 prompt；若未来要支持旧 prompt 恢复，需另补内容指纹校验与重载步骤。
5. 落证据 `m5-drill-graylist-memory-isolation.md`（模板同 Task 1，加：白名单/版本键值序列、各步 trace 的 persona_version 与 memory_selected_ids、验收②判定行）。

- [ ] **Step 3: 成本打满分档演练（验收③）**

1. 取今日 UTC 键名：`quantabot:cost:$(date -u +%Y%m%d)`（Windows PowerShell：`"quantabot:cost:" + (Get-Date).ToUniversalTime().ToString("yyyyMMdd")`）。先记录 `ORIGINAL_EXISTS`、`ORIGINAL_VALUE=GET <今日成本键>`、`ORIGINAL_PTTL=PTTL <今日成本键>`；全程使用 `try/finally` 或等价 Redis 脚本保护恢复，绝不直接覆盖后 `DEL`。
2. **吃紧档**：在临时阈值窗口把同一真实键设置为 `21000`（`EX/PX` 使用已记录的原 TTL；原键不存在才用生产 `cost_key_ttl_hours`），等 ≥5s → 发 @ → 验证回复存在（**轻模型 Qwen3.5-Plus 真调**）、Langfuse trace `cost_tier=tight`、`light_model_used=true`；从该次 trace/SQLite 记录实际生成 `cost_li` 增量 `DRILL_TIGHT_LI`，不要把临时预置值当成演练费用。
3. **枯竭档**：再把同一键临时设置为 `28000`（仍不删除原键，并沿用剩余 TTL）→ 等 ≥5s → 发 @ → 验证 SQLite 新行 `decision=skipped_cost_exhausted`、demo0 无回复、Langfuse **无新 generation**（零 LLM 调用）。记录第二次实际生成费用（通常为 0）与两次 trace/comment_id。
4. **恢复与对账（成功/失败都执行）**：在 `finally` 中恢复原始键语义——原键存在则写回 `ORIGINAL_VALUE + DRILL_TIGHT_LI + DRILL_EXHAUSTED_LI` 并恢复 `ORIGINAL_PTTL`；原键不存在则写入演练实际费用之和并使用生产 `cost_key_ttl_hours`，让当天真实费用不丢失。验证恢复值、TTL 与同日 SQLite/Langfuse 生成口径对账；失败时也必须留下恢复结果，不得以 `DEL` 收尾。
5. 落证据 `m5-drill-cost-tier.md`（含两档 trace 字段、原值/临时值/实际费用增量/恢复值、TTL、失败清理结果与对账判定）。当前 `cost_li` 只代表已接线的生成 estimated cost，不宣称供应商全量账单。
