## 1. 选型方法论

### 1.1 评估维度定义（1-5 分）

| 维度 | 权重 | 定义 |
|---|---|---|
| LLM/Agent 生态 | **25%** | 本项目核心是 LLM 调用+记忆+评测，生态决定开发效率上限 |
| 开发效率 | **20%** | MVP 交付速度：样板代码量、调试便利性 |
| 与主服务集成 | **15%** | 与 Java demo0 对接成本（契约复杂度、联调难度） |
| 可控性/可测性 | **15%** | 链路透明度、可单测性、调试排错能力（对应"静默优于乱回"红线） |
| 运维成本 | **10%** | 部署复杂度、监控、故障面 |
| 学习曲线 | **10%** | 团队上手成本 |
| 长期风险 | **5%** | 社区活跃度、版本稳定性、被淘汰风险 |

### 1.2 项目特性（约束选型的硬边界）

1. **瓶颈在 LLM 延迟**（P95 ≤ 30s），服务本身计算轻 → 语言原生性能几乎不重要；
2. **与 Java 主服务跨语言 HTTP/MQ 通信**（PRD 已确认可行）；
3. 单实例部署（设计方案"明确不做"：不做分布式配额）；
4. 红线要求：审核前置、幂等、熔断分设、决策日志、kill switch——**这些是自控代码，框架越薄越容易实现**；
5. 评测是发布纪律（"改人格必须过评测"）——评测基础设施必须一等公民。

## 2. D1：Agent 服务语言/框架

### 2.1 候选方案

| 方案 | 技术栈 | 一句话定位 |
|---|---|---|
| A | **Python 3.12 + FastAPI** | LLM 应用领域事实标准 |
| B | Java 21 + Spring Boot 3 | 与主服务同栈，企业级稳定 |
| C | Node.js 20 + TypeScript + Fastify/NestJS | 前后端同语言，异步 IO 好 |
| D | Go 1.22 + gin/echo | 部署极简、性能强 |

### 2.2 详细对比矩阵

| 维度 | A: Python+FastAPI | B: Java+Spring | C: Node+TS | D: Go |
|---|---|---|---|---|
| LLM/Agent 生态 | **5**：OpenAI/DeepSeek SDK、httpx、prompt 工具、Ragas/DeepEval、LangChain 系全部 Python 优先；LLM 相关新库 90% Python 首发 | 2：Spring AI 可用但生态薄，评测/记忆库缺位，遇到坑社区答案少 | 3：OpenAI SDK 有，但评测生态（Ragas 等无）弱于 Python | 1：几乎裸调 HTTP，LLM 应用生态空白 |
| 开发效率 | **5**：类型提示+Pydantic 契约即文档；prompt 调试（jupyter/脚本）随改随跑；改人格/评测脚本无需编译 | 3：样板代码多；改 prompt 需重启；与"高频改人格"的工作模式相性差 | 4：TS 类型好，迭代快 | 3：代码量中等，但样板不少 |
| 与主服务集成 | 4：HTTP（httpx）+ MQ（pika/aio-pika）成熟，跨语言只靠契约；联调需 postman/httpie | **5**：同栈可共享 DTO 定义与经验，MQ/HTTP 客户端即 Spring 生态原生 | 4：HTTP/MQ 客户端成熟（amqplib） | 4：net/http 原生强，MQ 库（rabbitmq/amqp091-go）可用 |
| 可控性/可测性 | **5**：pytest 是评测集最佳载体；链路全自控；uv 依赖锁 | 4：JUnit 成熟，但 LLM 输出断言工具链少 | 4：vitest/jest 可用 | 4：testing 原生好 |
| 运维成本 | 4：单容器部署简单；内存占用中 | 3：JVM 内存开销大；启动慢 | 4：部署简单 | **5**：单二进制，部署最优 |
| 学习曲线 | **5**：语法门槛最低 | 4：团队若熟 Java 则 5 分，但 LLM 应用模式仍是新知识 | 3：需 TS 熟练度 | 2：并发模型与错误处理学习成本高 |
| 长期风险 | 5：AI 应用第一语言，5 年内地位稳固 | 5：JVM 长青，但 LLM 应用侧存在感弱 | 4：AI 应用侧被 Python 压制 | 3：LLM 应用赛道无存在感，招人/找参考难 |

### 2.3 加权评分

| 方案 | 生态 25% | 效率 20% | 集成 15% | 可控 15% | 运维 10% | 学习 10% | 风险 5% | **总分** |
|---|---|---|---|---|---|---|---|---|
| **A: Python+FastAPI** | 1.25 | 1.00 | 0.60 | 0.75 | 0.40 | 0.50 | 0.25 | **4.75** |
| B: Java+Spring | 0.50 | 0.60 | 0.75 | 0.60 | 0.30 | 0.40 | 0.25 | 3.40 |
| C: Node+TS | 0.75 | 0.80 | 0.60 | 0.60 | 0.40 | 0.30 | 0.20 | 3.65 |
| D: Go | 0.25 | 0.60 | 0.60 | 0.60 | 0.50 | 0.20 | 0.15 | 2.90 |

### 2.4 结论与理由

**选 A：Python 3.12 + FastAPI。**

1. **生态权重最高且差距悬殊**：本项目的 4 个核心工作（LLM 调用、记忆管理、人格评测、模型评审）在 Python 都有一等公民工具链，其他语言要么缺评测生态、要么缺 LLM 工具库——选其他语言等于自建轮子；
2. **工作模式匹配**：人格与 prompt 是"高频改、快验证"的研究型迭代，Python 改完即跑，Java 需编译重启，摩擦大；
3. **跨语言集成不构成阻碍**：PRD 已确认 Java/Python 靠 HTTP+MQ 契约通信，D4/D9 方案落地了具体客户端；
4. **性能无关**：瓶颈在 LLM 延迟（秒级），FastAPI 异步吞吐（万级 RPS）远超需求。

**落选理由**：
- Java：最大诱惑是"同栈"，但 LLM 生态分（2/5）是硬伤——评测集（Ragas/DeepEval）、记忆工具、模型评审都没有对应物，省下的集成成本会加倍还到自建上；
- Node+TS：无明显短板但无长板，LLM 评测生态弱；
- Go：部署最优但 LLM 赛道生态空白，学习曲线也不匹配"快速改人格迭代"的工作模式。

## 3. D2：Agent 编排框架（Python 生态内，对照 2026 业界格局）

> 2026 年格局关键变化：**AutoGen 已进维护模式**（不再是安全默认）；OpenAI Agents SDK 脱离单厂锁定；轻量级新贵（PydanticAI/Agno/smolagents）崛起。更重要的是 **Anthropic 官方工程博客结论：最成功的 Agent 实现使用"简单、可组合的模式"而非复杂框架**——这是本决策最重要的外部背书。

### 3.1 候选方案（业界主流全景）

| 方案 | 定位 |
|---|---|
| A | **纯 FastAPI 自组链路**：触发→决策→上下文→生成→落库，普通函数+显式状态对象 |
| B | LangChain（LCEL Chain） | 组件化链式调用，生态最大 |
| C | LangGraph | 状态机图编排，企业级 Agent 流程控制（2026 生产默认推荐之一） |
| D | LlamaIndex（Agent 模式） | 检索优先，RAG 场景强 |
| E | CrewAI | 多 Agent 角色协作原型最快（AutoGen 维护模式后替代者之一） |
| F | **PydanticAI** | 轻量类型安全派：FastAPI 风格 API、类型即契约、Logfire 可观测 |
| G | **Agno（原 Phidata）** | 轻量性能派：宣称比 LangGraph 快 5000 倍实例化、内存少 50 倍 |
| H | **smolagents（HF）** | 极简派：核心 ~1000 行，CodeAgent 写 Python 代码作行动 |

### 3.2 详细对比矩阵

| 维度 | A: 自组 | B: LangChain | C: LangGraph | F: PydanticAI | G: Agno | H: smolagents |
|---|---|---|---|---|---|---|
| 链路匹配度 | **5**：单 Agent 固定线性链路+条件分支，自组即最简形态 | 3：抽象与需求错位 | 3：图编排价值在多 Agent/复杂循环/断点续跑，本项目全没有 | 3：单 Agent 支持，但依赖注入/结果类型验证是本项目不需要的重量 | 3：轻量但多 Agent 编排导向 | 3：CodeAgent 的"代码即行动"范式适合工具编排，不适合人格回复链路 |
| 可控性/可测性 | **5**：普通函数 pytest 直测；决策日志=函数打点 | 2：抽象厚 | 3：LangSmith 好但平台依赖 | 4：类型安全好 | 3 | 3 |
| 红线实现成本（幂等/熔断/kill） | **5**：横切全自控 | 2：对抗框架默认行为 | 3 | 3：可插但多一层 | 3 | 2 |
| 人格/模式切换 | **5**：prompt 纯字符串（git 版本化），模式路由一个函数 | 3 | 3 | 3 | 3 | 3 |
| 版本稳定性 | **5**：只依赖 FastAPI | 1：breaking 惯犯 | 3：发布快但规范 | 2：**post-0.x 期，API 还在变** | 3：MPL-2.0，34K star 活跃 | 3：有改名 breaking 史（ApiModel→HfApiModel） |
| 学习/依赖成本 | **5**：零新概念 | 3 | 2 | 3：FastAPI 用户学习成本最低 | 3 | 2：代码执行+沙箱概念 |
| 生产成熟度 | **5**：成熟件组合 | 4 | **5**：生产验证最充分 | 2：Assess 级（雷达未到 Trial） | 3：Trial 级 | 2：JetBrains 评"生产特性薄"，本地执行器非沙箱 |

### 3.3 加权评分

| 方案 | 链路 25% | 可控 15% | 红线 15% | 人格 10% | 稳定性 15% | 学习 10% | 生产 10% | **总分** |
|---|---|---|---|---|---|---|---|---|
| **A: 自组** | 1.25 | 0.75 | 0.75 | 0.50 | 0.75 | 0.50 | 0.50 | **5.00** |
| B: LangChain | 0.75 | 0.30 | 0.30 | 0.30 | 0.15 | 0.30 | 0.40 | 2.50 |
| C: LangGraph | 0.75 | 0.45 | 0.45 | 0.30 | 0.45 | 0.20 | 0.50 | 3.10 |
| F: PydanticAI | 0.75 | 0.60 | 0.45 | 0.30 | 0.30 | 0.30 | 0.20 | 2.90 |
| G: Agno | 0.75 | 0.45 | 0.45 | 0.30 | 0.45 | 0.30 | 0.30 | 3.00 |
| H: smolagents | 0.75 | 0.45 | 0.30 | 0.30 | 0.45 | 0.20 | 0.20 | 2.65 |

### 3.4 结论与理由

**选 A：纯自组。**

1. **本项目链路形态决定**：单 Agent、固定线性链路（触发→决策→上下文→生成→落库）+ 2-3 个条件分支。图编排/多 Agent/断点续跑等框架卖点本项目全部用不到——**为不存在的复杂度买框架，是负资产**；
2. **红线体系决定**：幂等、熔断、频率、kill switch、决策日志全部要求"插在我自己的代码里"。框架层越厚，这些横切代码越要"绕过框架默认行为"，出错面越大；
3. **人格高频迭代决定**：prompt/人格管理走 git 版本化 + 评测回归，纯字符串+函数最顺；框架的 PromptTemplate 反而多一层绑定；
4. **版本风险**：LangChain 系的 breaking change 史是选型一票否决项（人格事故回滚时最怕框架行为漂移）。

**落选理由**：
- LangGraph 是"最像正经选择"的落选者：若未来 Phase 3 出现多场景循环/人工介入节点，可**再评估引入**（自组代码迁 LangGraph 成本可控，反之则贵）——本文档显式预留此升级路径；
- LangChain：生态最大但抽象与稳定性双差，社区已大量"从 LangChain 退回自组"的案例；
- LlamaIndex：本项目检索在主服务（D4），Agent 不需要本地 RAG 编排；
- CrewAI/AutoGen：多 Agent 协作框架，与单 Agent 项目形态根本错配。

## 4. D3：LLM 选择（含模型原生人格维度）

> QuantaBot 是**人格驱动产品**，模型自身的"出厂气质"会透过滤镜层显现在回复里——选型必须把"模型人格与产品人格的兼容性"作为一等维度，而不只看跑分。

### 4.1 模型原生人格与文风（业界实测数据）

| 模型 | 原生人格/文风 | 关键实测依据 |
|---|---|---|
| **DeepSeek** | "冷淡又闷骚的极客气质"：推理干脆、逻辑最严密、理工科瞬态响应凌厉；**文字共情偏弱**，抒情/安慰场景容易生硬；大五宜人 97.5% 但 16 型三次测出不同结果（人格稳定性中） | 大模型性格测试（宜人 97.5%，INFJ→INFP→INTJ 漂移）；高考安慰实测中"先讲道理"倾向 |
| **豆包 (Doubao)** | "接地气的暖"：文风最自然（小红书/公众号风格）；**安慰实测第一**——先认情绪不说教、把安抚翻译成具体动作、给说得出嘴的话术、不催促崩溃者做大决定；宜人 97.9%（INFP） | 高考六模型安慰横评冠军（雷科技）；性格测试宜人度第一 |
| **Qwen** | 偏严谨学术风：报告/论文最佳，B 端文档风；创意放飞时拘谨 | 国产横评（2026 年中） |
| **Kimi** | 文学性气质：长篇创作有惊喜、信息收纳强；短篇平淡灵气不足 | 长横评与创作者口碑 |
| **GLM** | 中规中矩，推理强项（GPQA 高），人设稳定性口碑一般 | 横评数据 |

### 4.2 与 QuantaBot 人格的兼容性分析

QuantaBot 人格 = **统一内核（学长学姐底色）+ 4 场景模式**（专业答疑/生活玩梗/情绪陪伴/治理）。模型兼容性矩阵：

| 模式 | DeepSeek 兼容度 | 豆包兼容度 | Qwen 兼容度 | Kimi 兼容度 |
|---|---|---|---|---|
| 专业答疑（严谨+一点幽默） | **5**（逻辑严密是刚需） | 3（严谨性弱） | 4 | 3 |
| 生活玩梗（松弛、接梗） | 3（"闷骚极客"可玩梗但偏冷） | **5**（接地气最自然） | 2（学术腔难松弛） | 3 |
| 情绪陪伴（共情、极短、不说教） | 2（**共情是已知短板**） | **5**（安慰实测第一） | 3 | 4 |
| 治理（克制、教学式拒绝） | **4**（分寸感稳） | 3（太宜人，拒绝变软） | **4** | 3 |

**结论：没有任何单一模型在 4 个模式都最优——豆包和 DeepSeek 是互补的两极。**

### 4.6 结论与理由

**选 A：DeepSeek 主模型 + Qwen 轻量降级档 + prompt 人格补偿层**（在管理员已拍板"混合降级"基础上的细化）。

1. **人格短板可以用 prompt 层系统性补偿**：DeepSeek 的共情弱是"风格缺省"而非"能力缺失"——人格内核 prompt（PRD F3）+ 模式切换 + PRD 7.5 评测样例的 rubric 正是为补偿而生；且"闷骚极客+高宜人"的底色对"学长学姐"人设其实是**安全的基础**（不油不谄媚）；
2. **一致性压倒单场景最优**：方案 C 场景化路由的致命伤是**跨模型人格断裂**——"记仇/老熟人"跨场景记忆要求同一个"我"，豆包答的题 DeepSeek 接不住语气（PRD F3 人格一致性评测=内核不变+模式切换正确，跨模型直接违反）；
3. **成本结构最优**：DeepSeek 缓存命中 ¥1/M 输入（人格内核 prompt 是固定前缀，**缓存命中率天然高**）；降级档 Qwen3.5-Plus（¥0.8/M，比主模型便宜 15 倍）；
4. **与主服务同源**：账号/密钥/网络全复用，少一个外部依赖。

**落选理由**：
- 豆包为主：情绪场景最强但答疑严谨性（MVP 12/17 个场景是答疑/治理类）和逻辑密度的短板更大，且主服务无存量依赖；
- 场景化路由：人格一致性一票否决（见上），**作为 Phase 3 升级预留**（若情绪场景占比超 40% 且用户反馈共情不足，单列"情绪陪伴专用模型路由"再评估）；
- Qwen 为主：人格兼容垫底（学术腔与"接梗学长"人设冲突最大），只配做降级档。

**风险与缓解**：
- DeepSeek 情绪场景共情不达 PRD 7.5 样例标准 → **评测集把情绪陪伴 3 场景设为一票否决项**（不达标不上线），不达标则优先调人格 prompt，仍不行再触发升级预留；
- 人格补偿 prompt 与模型原生气质对抗导致表达不稳定 → 评测回归覆盖（AGENTS.md"改人格必须过评测"）。

### 4.7 成本配额实时累计载体（缺口 G6，业务实现规格）

**Langfuse 是观测平台（事后看），不是实时预算控制器。** 实时分档判定需要一个"当前花到哪一档"的即时计数：

- **载体**：Redis 日累计键 `quantabot:cost:{yyyymmdd}`，每次 LLM 调用前读键分档（充足→主模型 / 吃紧→轻模型 / 枯竭→规则兜底），调用后按实际 token 计费折算 `INCR` 累加，键 `EXPIRE 48h` 防残留；
- **对账口径**：Redis 日累计为**实时控制**依据，Langfuse 逐次记录为**事后核对**依据，两者每日对账（统计口径与决策日志一致：诚实记账，超时/拦截的调用不计入成本）。

### 5.1 候选方案

### 5.2 详细对比矩阵

| 维度 | A: MQ收+HTTP发 | B: 全HTTP轮询 | C: 全MQ | D: Webhook |
|---|---|---|---|---|
| 触发实时性 | **5**：事件即推，秒级 | 1：轮询间隔=响应延迟下限；间隔小则空转压力 | **5** | **5** |
| 幂等实现 | **5**：MQ 消息自带 message id，天然幂等键（重复投递是 MQ 已知行为，幂等是标配解法） | 3：轮询要自己记游标，游标丢失=重放 | 3 | 3 |
| 主服务改动量 | **3（最小可行）**：主服务已用 Outbox→MQ 模式（`OutboxEventMapper` 已存在），评论事件大概率只需**新增一个 topic/binding** | **4**：几乎零改动（Agent 拉现有接口） | 1：写库/检索改 MQ 需主服务新增消费方+应答机制，**违反"主服务最小改动"** | 2：主服务要实现回调重试/签名 |

| 实现复杂度 | **4**：pika/aio-pika 消费者 + httpx 客户端，都是成熟件 | **5**：最少代码 | 1 | 2：回调安全（签名/重放）要自建 |

### 5.4 结论与理由

**选 A：RabbitMQ 收事件 + HTTP 发请求**（管理员已拍板）。在 v1.2 基础上补齐实现级规格：

1. **两种语义各归其位**：事件获取是"订阅推送"（MQ 强项），写库/检索/审核是"请求-响应"（HTTP 强项）——A 是唯一两个语义都对的方案；
2. **幂等键来源（缺口3，写死）**：Outbox 为**至少一次投递**，message id 是投递层概念、可能重投。**业务唯一键 = 主服务评论 ID（comment_id）**。去重表以 comment_id 为键；message id 仅作投递去重的辅助；
3. **主服务改动最小且方向已铺好**：demo0 已有 Outbox→MQ 基础设施（`OutboxEventMapper`），Agent 侧只需消费新增的评论触发事件；
4. **故障语义正确**：Agent 宕机消息堆积不丢，恢复续跑——契合"AI 服务故障不影响主社区"的边界。

**落选理由**：
- 全 HTTP：轮询延迟+空转+幂等游标自管，三项全输；
- 全 MQ：同步调用硬套异步通道（correlation id+应答队列），复杂度爆炸且主服务要大改——违反"最小改动"；
- Webhook：主服务要自建回调重试/签名/防重放，改动量与安全面都更差。

**具体技术件**：消费端 `aio-pika`（异步，配合 FastAPI 事件循环）；契约=主服务评论落库事件新增 AI 触发字段（Phase 0 定契约）。

### 5.5 业务链路实现规格（D4 配套，缺口 1/2/G5/G7）

**① 评论树/帖子详情读取接口（缺口1，上下文组装数据源）**

Agent 从主服务只拿：MQ 事件（新评论本体）、检索接口（语义碎片）、写库。**没有任何数据源提供"帖子楼层结构"**——RAG 给的是碎片，不是"第3楼回复第1楼"的父子链；没有父链，AI 不知道在回复谁，人设穿帮。

- **Phase 0 契约项**：主服务新增带鉴权接口，返回：帖子主楼、@评论及其父链、相关楼层讨论脉络、AI 历史发言（按 AI user_id 标记）；
- **不可降级**：评论树不可用 → 链路无法组装上下文 → **不可上线**（唯一无降级路径的依赖，见 Risks）。

**② 并发与同帖串行化（缺口2）**

MQ 消费者天然并发，同一帖两人同时 @ 会基于"没有彼此"的上文组装（穿越）。

- **决策：单消费者 + 同帖按 post_id 串行**——最简单用单消费者（天然串行），或按 post_id hash 分发到同一 worker；
- 同帖消息组装上下文时带上"本消息触发前的最新楼层快照"，保证后回的消息能看到前一条 AI 回复。

**③ Kill switch 触发通道（缺口G5，控制面物理连通）**

Agent 是独立服务，运营后台（demo0-admin）无法直接控制它。**决策：Redis 配置键广播**：

- 主服务/运营写 `quantabot:switch:kill`（true/false），Agent 消费者循环每 N 秒（≤5s）读键，true 即暂停消费+停止回复（满足 PRD"5 分钟止血"）；
- 灰度白名单/人格版本同样走 Redis 配置键（`quantabot:switch:graylist` 等）；
- 运营侧只需一个写 Redis 的入口（admin 页面或运维脚本）；回滚 = 配置键改回旧人格版本号；
- 兜底：Redis 极端不可用时，MQ 消费暂停仍是止血手段。

**④ 政策咨询内容源确认（缺口G7，Phase 0 项）**

主服务 RAG 索引的是**社区帖子/回答**（ContentVectorSyncService/AnswerVectorSyncService），**非政策文件库**——PRD 场景 6"命中知识库给权威答案"现状下无内容源。Phase 0 必须与主服务 Owner 确认：① 政策文档（奖助学金/学分/版规）是否已进 RAG 索引；② 若无，主服务是否配合导入；③ 若都不行，场景 6 MVP 边界降级为"基于社区已有政策帖讨论回答，无权威来源直说不知道"（不编造红线兜底）。

### 5.6 决策层设计（业务链路补充）：低价值过滤 + 场景模式识别

> 链路 ② 决策层是 Agent 的"大脑"，承担两个职责：**该不该回**（成本与穿帮风险闸门）+ **什么模式回**（4 场景表达模式路由）。两者合并为**一次轻量模型调用**输出（省成本）。

**1. 低价值过滤（"没营养"判定）= 成本漏斗，越靠前越便宜**

| 层 | 手段 | 成本 | 覆盖 | 判定 |
|---|---|---|---|---|
| ① 硬规则层 | 正则/查表：超短、纯 emoji/纯标点/纯链接、重复字符（"哈哈哈"）、黑词表（广告/引流/代写） | 零 | 60-70% | 直接不回 |
| ② 轻量分类层 | 便宜模型三分类：值得回 / 不值得回 / 拿不准 | 低 | 灰色地带 | 见下"保守方向" |

- **保守方向（关键权衡）**：被动 @ 是"宁回勿漏"（用户 @ 了预期高，@ 了不回是体验伤害）；主动拉活是"宁漏勿回"（自己凑上去，回错被截图风险大）。同一判定标准，两场景保守方向相反。
- 规则层挡下的"哈哈哈"等**不丢弃**，登记为"楼内气氛"信号，供上下文组装参考。

**2. 场景模式识别 = 结构化信号粗分 + LLM 意图分类收口**

- **① 结构化信号（免费、先粗分）**：帖子分区（生活/专业→偏答疑）、主楼内容类型标签（求助→答疑；吐槽→陪伴/玩梗）、触发评论句式（"XX课怎么选"→答疑；"你评评理"→玩梗；"好难过"→陪伴；"帮我骂人/代写"→治理）。
- **② LLM 意图分类（模糊地带）**：喂"主楼 + 触发评论 + 最近楼层"，输出结构化结果——
  ```
  { "值得回": true, "模式": "生活玩梗", "置信度": 0.85, "理由": "用户明显玩梗求互动" }
  ```
  模式 ∈ 专业答疑 / 生活玩梗 / 情绪陪伴 / 治理。
- **防串味**：模式判定进决策日志（Langfuse trace，"为什么判为玩梗"可回查）；评测集加"模式错配"硬伤用例（答疑判成玩梗 = 穿帮，规则断言抓）。

**3. 决策器产出 → 生成层的输入契约**
决策器输出 `{值得回, 模式, 置信度, 需要检索: bool, 需要记忆: bool}`，直接驱动链路后续：不值得回→静默（记决策日志）；值得回→按模式选 prompt、按 flag 决定是否调 RAG 检索/记忆读取。

## 6. D5：记忆三层存储（向量数据库底座）

> **v1.2 修正**：原方案"用户级/长期级用 MySQL"经复核推翻——记忆检索本质是**语义召回**（"上次聊保研焦虑，这次复试帖要接上"关键词匹配做不到），且**主服务"向量库"被证伪**（见 6.0）。本节改为：向量数据库选型为记忆底座。

### 6.0 关键发现：主服务"向量库"不可复用（证伪）

查证 demo0 代码：`VectorStorePersistenceService` 用的是 **Spring AI 的 `SimpleVectorStore`**——纯内存 Java 对象 + JSON 文件快照（`vector-store/content-vector-store.json`），源码注释明示"应用重启后所有向量数据会丢失"。

| 证伪理由 | 说明 |
|---|---|
| 语言不可达 | Java 进程内对象，Python Agent 无法访问 |
| 可靠性不达标 | 内存实现，非数据库级持久化 |
| 无元数据过滤 | 记忆隔离（user_id）刚需无法满足 |

**结论：Agent 必须自建向量能力，"复用主服务向量库"路径不存在。**（PRD 7.3 技术约束中"主服务已有向量库可用"的说法同步作废）

### 6.1 记忆框架层对比（业界主流，决定"用什么模式"）

| 方案 | 架构核心 | 关键结论 |
|---|---|---|
| **Mem0** | 两段式：提取候选事实 → 与现有记忆比对决策 **ADD/UPDATE/DELETE/NOOP**；存储底座**就是可插拔向量库（Qdrant 为官方默认之一）** | **模式被完整吸收**（四态决策），且其底座选 Qdrant = 本节选型与业界默认对齐 |
| Zep (Graphiti) | 时间知识图谱（双时间戳+失效标记） | 图数据库过重；**时间戳失效思想被吸收**（persona_version） |
| Letta (MemGPT) | Agent 自主决定记什么 | 人格漂移黑箱，与"决策日志可审计"冲突，一票否决 |
| LangChain Memory | 原语集合，机制全手写 | 等于加依赖的自建 |

### 6.4 加权评分（过滤 25% / 部署 10% / Python 生态 10% / 持久化 15% / 四态 15% / 成熟度 15% / 运维 10%）

|---|---|---|---|---|---|---|---|---|
| **Qdrant** | 1.25 | 0.40 | 0.50 | 0.75 | 0.75 | 0.75 | 0.40 | **4.80** |
| Chroma | 0.60 | 0.50 | 0.50 | 0.45 | 0.60 | 0.30 | 0.50 | 3.45 |
| Milvus | 0.80 | 0.10 | 0.40 | 0.75 | 0.60 | 0.75 | 0.10 | 3.50 |
| Weaviate | 0.80 | 0.30 | 0.40 | 0.75 | 0.60 | 0.60 | 0.30 | 3.75 |

| LanceDB | 0.80 | 0.50 | 0.50 | 0.60 | 0.60 | 0.45 | 0.50 | 3.95 |

### 6.5 结论与理由

**选 Qdrant**（独立 Docker 服务，`qdrant-client` async 接入）。

1. **记忆隔离是隐私红线，而 payload 过滤恰是 Qdrant 的绝对强项**：查询模式 `filter(user_id=X, persona_version=Y) + 语义 top-k` 与 Qdrant 的 filter pushdown + HNSW 设计一一对应，多份独立评测（学术论文+两份生产横评）共同认定其复杂谓词过滤不掉性能——这是 Chroma/FAISS 的结构性短板；
2. **与业界记忆方案底座对齐**：Mem0 官方默认底座即 Qdrant——"自建 Mem0 模式 + Qdrant 底座"等于站上业界主流组合，升级到 Mem0 self-host 时底座零迁移；
3. **规模-成本甜蜜点**：十万级向量对 Qdrant 是轻负载（单容器+快照备份即可），对 Milvus 是杀鸡用牛刀（组件全家桶运维成本远超收益）；
4. **人格不失忆的可靠性**：数据库级持久化语义 vs Chroma 的进程内 SQLite——"记得你"是产品核心资产（PRD P3 高光场景），重启丢记忆=穿帮。

**落选理由**：
- **Chroma**：最快上手（嵌入式零部署）是唯一优势，但过滤/持久化/生产口碑三项全弱——原型可用、产品核心资产存储不赌；
- **pgvector**：过滤和事务其实最强，但要**引入 PostgreSQL**——对一个 MySQL 存量的项目是比向量库更重的新组件（若未来引入 PG 可重评）；
- **Milvus**：十亿级能力与十万级需求严重错配，etcd/Pulsar/MinIO/K8s 运维负担一票否决；
- **FAISS**：是 ANN 算法库不是数据库（无过滤/持久化/并发管理——学术评测原话），用它等于自建数据库；
- **Weaviate**：无明显短板，但过滤与延迟均逊 Qdrant，模块化（内置 embedding）对自组链路是多余重量；
- **LanceDB**：嵌入式+新项目，生产验证不足；
- 云托管（Pinecone 等）：数据出境+付费，直接违反隐私红线。

### 6.6 新分层方案（MySQL 退出记忆链路）

| 层 | 存储 | 理由 |
|---|---|---|
| **对话级** | Redis（TTL） | 完整楼层链，TTL 自然衰减——不变 |
| **用户级 + 长期级** | **Qdrant** | 记忆 = 文本事实 + 向量 + payload（`user_id` / `persona_version` / `memory_type` / `timestamp` / `status`）；四态决策 = Qdrant upsert/delete-by-filter/payload 覆盖 |
| **决策日志/观测（缺口4）** | **Langfuse（自托管，网页看轨迹/成本）+ SQLite（本地决策明细落盘）** | 决策日志消费方是运营/复盘/Phase 3 后台，但**不必双写主服务 MySQL**——Langfuse 网页直接看每次 run 完整轨迹，比主服务改造更便宜 |

**决策日志可见性（v1.4 改用 Langfuse，替代双写 MySQL）**
- **消费方是谁**：Agent 自查 / 运营查举报（"AI 当时为什么这么回"）/ Phase 3 管理后台"AI 思考轨迹" / 每条回复成本观测（PRD Objective 成本指标）。
- **怎么被看到**：Agent 加 `tracing.py`（接入 Langfuse，三个环境变量即通），每次 run 自动记录：输入上下文、决策器输出（值得回/模式/理由）、生成文本、审核结果、token 与费用。运营/复盘打开 **Langfuse 网页直接看轨迹与成本**，无需主服务加表/加查询页。
- **本地 SQLite**：保留决策明细落盘（Langfuse 断连时近端兜底 + Agent 侧自查），不做主服务同步。
- **为什么替代双写**：双写 MySQL 需主服务加表+写库入口+后台查询页；Langfuse 一个容器 + tracing.py 同时解决"决策日志可见性 + 成本观测 + 调试验证"三件事，且不依赖主服务改造。

**Embedding 接入**（新增）：记忆写入需要向量化——Agent 直连 Qwen Embedding API（与主服务 `QwenEmbeddingConfig` 同模型同维度 1024，配置同源），不经过主服务（写入是 Agent 内部操作，无需绕行）。

**四态决策落地示例**：
```
写入：POST /collections/qb_memory/points
  { id, vector: embed(事实文本), payload: {user_id, memory_type, persona_version, status: "active", text} }

比对决策（同次 LLM 调用输出）：与该 user 现有记忆语义比对 →
  ADD     → 新 point 插入
  UPDATE  → 同 id upsert（payload 覆盖）
  DELETE  → delete by filter(user_id=X, memory_id=Y)（或 status→"invalid"，保留审计）
  NOOP    → 跳过

读取：POST /collections/qb_memory/points/search
  { vector: embed(当前帖子内容), filter: {must: [{user_id: X}, {persona_version: Y}, {status: "active"}]}, limit: 5 }
```

**v1.1 保留的业界模式吸收**：Mem0 四态决策（上）+ Zep 时间戳失效（`status`/`persona_version` payload 标记，人格变更后旧口径记忆失效不删除）。

## 7. D6：评测体系

### 7.1 候选方案

| 方案 | 说明 |
|---|---|
| A | **pytest 规则断言 + LLM-as-Judge（DeepSeek 评审）混合 + promptfoo redteam 注入专项（可选增强）** |
| B | 纯规则断言（关键词/结构/禁止词） |
| C | 纯模型评审（全主观维度交给 LLM 打分） |
| D | 评测框架全家桶（DeepEval / Ragas / promptfoo / LangSmith） |

> 业界 2026 格局速览：DeepEval=pytest 风格+预置指标（偏 RAG/Agent 轨迹）+SaaS 上推；Ragas=RAG 指标标准制定者；promptfoo=CLI+YAML+**红队（OWASP LLM Top10）**；LangSmith/Langfuse=追踪平台。**本项目指标全是自定义人格维度+注入对抗，预置指标错配是框架落选的根本原因。**

### 7.2 详细对比矩阵

| 维度 | A: 混合+注入专项 | B: 纯规则 | C: 纯模型评审 | D: 评测框架 |
|---|---|---|---|---|
| 客观维度覆盖（禁止词/长度/结构/身份标注） | **5**：规则断言确定性 100% | **5** | 2：LLM 判禁止词会漏（不确定） | 4 |
| 主观维度覆盖（语气/人格/玩梗质量/不说教） | **5**：LLM Judge 按 PRD 7.5 评判要点打分 | **1**：语气无法关键词断言 | 5 | 4 |
| **注入对抗覆盖（场景14 Prompt 注入识别）** | **5**：promptfoo redteam 覆盖 OWASP LLM Top10（提示注入/越狱/PII 泄露专项探测，正好是 PRD 治理场景的评测弹药库） | 2：注入变体无法穷举 | 3：可让 Judge 判但覆盖无保证 | 4 |
| 回归稳定性（跑两次结果一致） | **4**：规则部分 100%；Judge 部分靠温度 0 + 少量采样 | **5** | 2：全主观，波动大 | 3 |
| 成本 | **4**：Judge 只跑评测集（数十用例），成本可忽略 | **5**：零 LLM 成本 | 3 | 3 |
| "改人格必须过评测"门禁可执行性 | **5**：CI/本地一条命令（pytest），通过/失败明确 | 5 | 3：评分波动导致门禁标准漂移 | 4 |
| 与 PRD 7.5 验收样例衔接 | **5**：样例的"评判要点"直接翻译成断言+Judge rubric | 3：只能覆盖一半 | 4 | 4 |
| 上手/依赖成本 | **4**：pytest 团队已知 + 自写 Judge prompt；promptfoo 独立 CLI（不进 Python 依赖树） | **5** | 4 | 2：新框架概念+版本风险 |

### 7.3 加权评分

| 方案 | 客观 25% | 主观 25% | 注入 10% | 稳定 15% | 成本 10% | 门禁 15% | **总分** |
|---|---|---|---|---|---|---|---|
| **A: 混合+注入专项** | 1.25 | 1.25 | 0.50 | 0.60 | 0.40 | 0.75 | **4.75** |
| B: 纯规则 | 1.25 | 0.25 | 0.20 | 0.75 | 0.50 | 0.75 | 3.70 |
| C: 纯模型 | 0.50 | 1.25 | 0.30 | 0.30 | 0.30 | 0.45 | 3.10 |
| D: 框架 | 1.00 | 1.00 | 0.40 | 0.45 | 0.30 | 0.60 | 3.75 |

### 7.4 结论与理由

**选 A：规则断言 + LLM-as-Judge 混合，promptfoo redteam 作注入专项增强。**

1. **评测维度天然三分**：PRD 7.5 的评判要点=客观（不破防/不越界/身份标注）+主观（语气/接梗）+**对抗（注入识别，PRD 场景14）**——自写混合覆盖前两类，promptfoo redteam 补第三类（注入变体无法手工穷举，专业工具自动生成攻击向量）；
2. **门禁需要确定性**："过评测才能上线"是发布纪律，门禁标准不能漂移。规则层 100% 确定给出底线（穿帮类硬伤挡死），Judge 层温度 0 + 固定 rubric 给主观分；
3. **promptfoo 以独立 CLI 引入**（不进 Python 依赖树、不绑运行时），`promptfoo redteam run` 生成注入/越狱/PII 泄露攻击用例打 AI 账号，报告进发布门禁——**攻击面覆盖是手写评测做不到的**；
4. **DeepEval 落选关键**：它本质是"pytest + 预置指标 + G-Eval"的框架化——预置指标（faithfulness 等）偏 RAG/轨迹，我们全是自定义人格 rubric，等于为壳付依赖成本，且带 SaaS 上推（Confident AI）。

**落选理由**：
- 纯规则：主观维度+注入对抗双缺；
- 纯模型评审：门禁标准随评分波动，发布纪律变成概率游戏；
- 评测框架为主：指标错配（Ragas 管不到人格语气）或为壳付成本（DeepEval）；promptfoo 只取其红队子集。

### 10.1.1 核心链路（按数据流，服务化拆分）

主服务 demo0 只做"事件发出 + 结果写库"，Agent 逻辑全部在本仓库：

| 链路 | 职责 | 关键约束 |
|---|---|---|
| ① 触发层 | 被动：消费 MQ 事件检测是否 @ AI | 幂等键 = comment_id；同帖按 post_id 串行 |
| ② 决策层 | 判断"该不该回、什么模式回" | 成本漏斗过滤 + 场景模式识别，一次轻量调用 |
| ③ 上下文组装 | 调主服务评论树接口，组装主楼/楼层脉络/AI 历史发言 | 筛选策略 + 长度预算；帖子间严格隔离；**评论树不可用→不可上线** |
| ④ 生成层 | 人格内核 prompt + 4 模式 + 防幻觉护栏 | 不编造"楼主说过的话"、不编造校园事实/政策条文 |
| ⑤ 记忆层 | 对话级 Redis / 用户级+长期级 Qdrant | 四态决策（ADD/UPDATE/DELETE/NOOP）；payload 隔离 user_id |
| ⑥ 落库与推送 | 走主服务写库入口，复用推送通道 | 禁止绕过业务层 |
| ⑦ 横切保障 | 幂等/审核/熔断/频率/成本分档/决策日志/kill switch | 必须项缺一不上线 |

被动 vs 主动（Phase 2）处理差异：被动"宁回勿漏"（@ 了不回是体验伤害），主动"宁漏勿回"（回错被截图风险大）——同一决策器的保守方向相反，实现时体现为不同链路分支。

## 10.2 评测阈值细节（AGENTS.md §6 的完整版）

- **评测集规模**：PRD 7.5 三个验收样例为种子 + 17 场景各 1-2 用例（评测集 YAML 格式借鉴 globex：P0/P1/P2 rubric 三级 + deterministic 程序断言字段）。
- **一票否决项（P0，任一失败即门禁不通过）**：
  - 客观硬伤：破防/越界/编造楼主发言/编造政策条文/身份标注缺失/模式错配（答疑判成玩梗类）——规则断言 100% 挡死；
  - **情绪陪伴 3 场景**（求安慰/挂科失利/分享开心）：Judge 按 PRD 7.5 评判要点打分，**单场景得分 < 4/5 即不通过**（建议值，先跑评测集校准分布后可调整，调整需记录在版本记录）；
  - promptfoo redteam：注入/越狱/PII 探测**零成功**（出现一条成功攻击即不通过）。
- **回归冻结**：评测集用例跑分时冻结（不改 prompt、不改用例、关语义缓存），对比基线用同一冻结集；P95 时延退化 ≤20%、token 成本代理退化 ≤10% 作为参考阈值（借鉴 globex 发布门禁）。

## 10.3 部署细节（AGENTS.md §7 的完整版）

- **三容器 compose**：
  - `quanta-bot`（app，Python 3.12-slim 基础镜像，多阶段构建：uv 装依赖 → 仅拷 `src/ prompts/ eval/`；非 root 用户运行）；
  - `qdrant`（`qdrant/qdrant`，命名卷持久化 + 快照备份）；
  - `langfuse`（自托管镜像，自带其数据库容器，访问加基础认证）。
  - `[待确认]`：镜像 tag 固定版本号（锁 digest），首次构建时定。
- 独立部署（与主服务分离）；Agent 单实例单进程——**禁止双进程共用本地 SQLite/Qdrant 数据目录**（文件锁冲突，globex 教训）。
- **健康检查**：`/health` 返回 DB/Qdrant/Redis/MQ 连通性 + kill switch 当前状态；compose 配 healthcheck + `restart: unless-stopped`。
- **配置管理**：`.env`（不入库）+ `.env.example`（入库，含全部字段注释）；密钥只在 .env，禁止写死进代码/compose 文件。环境变量清单待 `infra/settings.py` 定稿后回填本节。

## 12. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 主服务不暴露检索/审核/评论树接口（依赖主服务 Owner） | Phase 0 对齐排期；**评论树不可用→链路无法组装上下文→不可上线（唯一无降级路径的依赖）**；检索不可用→降级"不引用社区内容直说不知道"；审核不可用→规则预检+人工抽查，**但不得跳过审核上线** |
| RabbitMQ 消息重复投递导致重复回复 | **comment_id 幂等键**去重（§5.4 缺口3；message id 仅投递层辅助） |
| 同帖并发触发导致回复穿越 | 单消费者 + 按 post_id 串行 + 楼层快照（§5.5 缺口2） |
| Python 生态依赖版本漂移（httpx/redis 大版本） | 锁版本（uv.lock）；依赖最小化 |
| DeepSeek 生成超时/限流 | 分设超时档 + 熔断（closed→open→half_open）+ 静默不回（PRD F6） |
| 记忆提取质量不达标（用户级口头禅/交情） | 评测集回归（A4 假设）；不达标先降级为对话级 |
| 选型锁定后难切换 LLM | LLM 供应商配置化（D3 已预留切换） |
| 政策咨询场景无权威内容源（G7） | Phase 0 确认政策文档入索引；否则场景 6 降级边界（见 §5.5 ④） |
| Kill switch 依赖 Redis 可用性 | Redis 与主服务共用实例（同机房）；极端情况 MQ 消费暂停仍是兜底止血手段 |

## 13. 升级预留（未来再评估，现在不做）

| 时机 | 可升级项 |
|---|---|
| Phase 3 出现多场景循环/人工介入 | 自组链路 → LangGraph（单向迁移成本可控） |
| **记忆机制复杂化（冲突消解/图关系/跨会话身份）** | **自建四态决策 → Mem0 self-host（Qdrant 底座零迁移）** |
| **情绪场景占比>40% 且共情评测不达标** | **情绪陪伴场景专用模型路由（引入豆包做情绪档）——人格断裂风险需单独评估** |
| 预算长期充裕 | 混合降级 → 单 DeepSeek 主模型 |
| 审核质量要求提升 | 规则预检 → 第三方内容安全 API |
| 引入 PostgreSQL 的任何契机 | Qdrant → pgvector 重评（SQL+向量一体） |
